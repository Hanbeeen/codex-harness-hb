# /recommit: 최종본 기준으로 커밋 다시 쌓기

작업 중에는 커밋을 기능별로 나눠 찍지만, 앞 커밋이 틀려서 뒤에서 고치는 일이 생긴다. 그러면 브랜치 이력에 `-던 것을 고침` 같은 흔적이 남고, PR 리뷰어는 실수와 수정 과정을 함께 읽게 된다. 이 스킬은 그 과정을 지워 **처음부터 기능별로 한 번에 짠 것처럼** 커밋을 다시 쌓는다.

## 원칙: A 는 끝까지 안 건드린다

```
A (원본)   base ── C1 ── C2 ── ... ── Cn        손대지 않음
             │
B (새로)     └── G1 ── G2 ── ... ── Gm          트리는 A 와 완전 동일
```

- **history rewrite 가 아니다.** A 를 그대로 두고 새 브랜치를 옆에 만든다. 실패하면 B 를 지우는 순간 원상복구가 끝난다.
- **백업 ref 도, 충돌 롤백도 필요 없다.** A 자체가 백업이다.
- 되돌리기 어려운 곳은 **6단계(교체) 한 곳뿐**이고, 거기에 게이트가 셋 있다.

## 절차

### 1-2) 점검 + 분석

```bash
bash $HOME/.agents/skills/recommit/scripts/analyze.sh [base]
```

스크립트가 브랜치, 워킹트리, base, 시크릿, 원격을 점검하고 아래 네 신호를 낸다. **diff 본문은 출력하지 않는다. 이 스킬이 커밋 diff 를 읽지 않는 것이 존재 이유다.**

| 섹션 | 읽는 법 |
|---|---|
| `COMMITS` | 커밋 번호, 제목, 건드린 파일 |
| `FILE SHARING` | 한 파일을 여러 커밋이 건드린 관계 |
| `TRACE` | **브랜치 안에서 자기 코드를 고친 관계 = 흔적.** 가장 강한 신호 |
| `SOLO FILE COMMITS` | 파일 1개짜리 커밋. 그 파일을 만든 커밋에 붙을 후보 |

중단되면 원인을 사용자에게 전하고 멈춘다. 임의로 우회하지 않는다.

### 3) 그룹 계획 수립 → 사용자 승인 (필수 관문)

신호를 근거로 그룹을 짠다. 판정 기준은 이 순서다.

1. **`TRACE` 에 나온 두 커밋은 반드시 한 그룹.** 그게 지우려는 흔적 자체다. 안 묶으면 이 스킬을 돌린 의미가 없다.
2. **`SOLO FILE COMMITS` 는 같은 파일을 만든 커밋에 붙인다.** 기능 직후의 주석/문서 커밋이 여기 걸린다.
3. **`FILE SHARING` 은 보조 신호.** 여러 커밋이 흔히 건드리는 공통 파일(라우터/엔트리포인트)은 신호가 약하다. 파일이 겹쳐도 **제목의 주제가 다르면 안 묶는다.**
4. 나머지는 **그대로 둔다.** 이 스킬은 정돈이지 통폐합이 아니다.

순서 규칙:

- 그룹의 위치 = 그 그룹에서 **가장 오래된 커밋의 자리**
- 그룹 안 커밋은 **번호 오름차순**으로 적용 (원래 순서 유지가 충돌을 막는다)
- 떨어진 커밋을 당기는 그룹은 계획표에 **충돌 가능**으로 표시

계획을 표로 내고 **멈춘다.** 승인 없이 4단계로 넘어가지 않는다. 표에는 그룹마다 묶는 커밋, 근거, 새 제목을 담고, 그대로 두는 커밋도 이유와 함께 적는다.

### 4-5) 재구성 + 검증

승인받으면 plan 디렉터리를 만든다. 위치는 scratchpad.

```
plan.txt      b: <base sha>            ← analyze.sh 마지막 줄에서 복사
              msg-01.txt 1
              msg-02.txt 2
              msg-03.txt 4 5 9         ← 한 줄 = 한 그룹
msg-NN.txt    각 그룹의 커밋 메시지 (UTF-8)
```

단독 그룹의 메시지는 원본을 그대로 쓴다: `git log -1 --format=%B <sha> > msg-NN.txt`

```bash
bash $HOME/.agents/skills/recommit/scripts/rebuild.sh <plan디렉터리> [B브랜치명]
```

스크립트가 계획을 먼저 검증하고(커밋이 전부 정확히 한 번씩 나오는지), B 를 만들어 cherry-pick 을 누적한 뒤, **A 와 B 의 트리 해시가 같은지**와 **커밋별 문법**을 확인한다. 어디서 실패하든 B 를 지우고 A 로 돌아간다.

| 종료코드 | 뜻 | 대응 |
|---|---|---|
| 2 | 충돌 | 그 그룹의 묶음을 풀거나, 사이 커밋까지 함께 묶어 재시도 |
| 3 | 빈 그룹 | 앞 그룹이 내용을 가져감. 그 그룹을 지우거나 합침 |
| 5 | 트리 불일치 | 재구성 실패. 계획을 다시 봄 |
| 6 | 문법 깨짐 | 그 커밋 시점에 파싱 안 됨. 해당 그룹을 합치면 해소 |

실패는 정상 경로다. A 가 멀쩡하므로 계획을 고쳐 다시 돌리면 된다.

### 6) 교체 (되돌리기 어려운 유일한 단계)

```bash
bash $HOME/.agents/skills/recommit/scripts/finalize.sh <A브랜치명> [--pushed-ok]
```

B 에 체크아웃한 상태에서 실행한다. 게이트 셋을 통과해야만 진행된다.

| 게이트 | 막는 것 |
|---|---|
| 1 트리 동일 | 내용이 다르면 교체 안 함 |
| 2 워크트리 점유 | 다른 작업 폴더가 A 를 쓰고 있으면 중단 |
| 3 원격 | A 가 push 돼 있으면 중단. `--pushed-ok` 를 붙여야 진행 |

**게이트 3 에 걸리면 사용자에게 알리고 명시 답변을 기다린다.** 교체하면 다음 push 가 force-push 가 되고, 그 사이 누가 pull 했으면 충돌한다. 이 확인을 건너뛰어 실제로 터진 적이 있다(2026-08-06, 8개 파일 both-added 충돌).

A 는 `refs/recommit-archive/<브랜치명>-<타임스탬프>` 로 옮겨진다. `git branch` 목록과 IDE 브랜치 메뉴에는 안 보이면서 언제든 꺼낼 수 있다.

### 7) 보고

전후 커밋 열, 사라진 흔적, 보존 ref 위치, force-push 필요 여부. **push 는 하지 않는다.**

## 커밋 메시지 정돈

`/commit` 의 형식/어투 규칙을 그대로 따른다. 여기에 더해:

- **단독 그룹은 원래 메시지를 그대로 쓴다.** 손대지 않는다.
- **합친 그룹만 새로 쓴다.** 최종 코드가 하는 일을 기준으로, 처음부터 그렇게 짠 것처럼.
- **브랜치 내부 경위를 드러내는 말을 지운다**: `QA 에서 드러남`, `직전 커밋의 X 를 고침`, `종전 판정이 틀렸음`. 원래 있던 버그를 설명하는 말은 지우지 않는다. 둘의 구분은 `TRACE` 가 알려준다. 지운 줄의 주인이 같은 브랜치의 앞 커밋이면 흔적이고, base 이전 커밋이면 정상적인 버그 수정이다.
- em-dash 금지, 완결형 종결 금지, 23줄 상한. `commit-msg` 훅이 재구성 중에도 그대로 돌아, 위반하면 그 자리에서 멈추고 B 가 지워진다. 계획 단계에서 미리 검사할 것: `node ~/.codex/harness/githooks/commit-msg <메시지파일>`

## 하지 않는 것

- 새 기능을 만들거나 코드를 고치지 않는다. 최종 내용은 A 와 한 바이트도 다르지 않아야 한다.
- 서로 다른 기능을 편의로 묶지 않는다. 파일이 겹친다는 이유만으로는 근거가 안 된다.
- `git push` 를 하지 않는다.
- 승인 없이 4단계/6단계로 넘어가지 않는다.

## 인자

base 브랜치명을 주면 그 기준. 없으면 `origin/main` → `main` 순으로 자동 감지.

## 브랜치 마무리 순서에서의 위치

`/check` → [사용자 검토] → `/recommit` → `/pr-draft` 중 3단계. 단독으로도 쓸 수 있다.
