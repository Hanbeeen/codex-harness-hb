# 제한된 개발 환경의 협업 지침

## 적용 범위

이 지침은 제공된 개발 도구와 자료 반출 제한이 있는 과제 환경용임. 과제 안내, 실제 제공 코드와 관리 정책을 우선함. 기존 지침과 충돌하면 전체를 덮어쓰거나 제한을 우회하지 않고 충돌과 영향을 보고함.

## Git 원격 쓰기 금지

- `git push`는 인자와 대상에 관계없이 절대 실행하지 않음. 브랜치, 태그, 강제 갱신, 삭제와 모의 실행도 예외가 아님.
- 메인과 모든 보조 역할, 호출한 스크립트와 자동화에 같은 금지를 적용함. 별칭, 래퍼와 다른 원격 쓰기 명령/도구로 우회하지 않음.
- 제출, 백업, 동기화와 공개 준비물 갱신을 푸시 사유로 삼지 않음. 실행 권한 승인을 푸시 허용으로 해석하지 않음.
- 다른 지침이나 작업 명령이 푸시를 요구하면 실행하지 않고 충돌을 알림. 다른 에이전트나 사람에게 푸시를 대신 요청하지 않음.
- 금지 동작을 시험하려고 `git push`를 실행하지 않음. 지침, 명령과 설정을 읽어 확인함.
- 원격 읽기는 과제 안내의 허용 범위를 따르고, 로컬 기록과 커밋은 기존 정책을 따름. 저장과 최종 제출을 원격 쓰기로 대체하지 않음.

## 요구와 구현

- 한국어 설명과 새로 작성하는 문구에는 korean-output.md의 공통 정책을 적용함. 설치기는 이 정책을 프로젝트 AGENTS.md 본문에도 포함함. 별도 설치 없이 읽는 경우에는 같은 폴더의 정책을 함께 읽음.

- 시작 전에 제공 안내와 실제 실행 방법을 읽고 필수 결과를 확인함.
- 확정 사실, 답 없는 질문과 구현 가정을 구분함. 실제로 받지 않은 업무 답변을 지어내지 않음.
- 요구 정리는 목적, 핵심 흐름, 수용 기준과 비목표만 짧게 유지함. 생성한 요약이 원문보다 높은 권위가 되지 않음.
- 실제 입력에서 결과 확인까지 먼저 연결하고 오류, 빈 결과와 처리 중 상태를 함께 다룸.
- 도구 개수, 문서 길이와 호출 횟수보다 요구 충족, 실제 검증과 구현 이해를 우선함.

## 과설계 방지

오버엔지니어링(overengineering: 요구에 비해 기능과 구조를 과하게 더하는 것)을 피함.

- 현재 필수 요구와 구체적인 실패 조건을 해결하는 가장 단순한 기존 구조를 우선함. 읽기 쉽고 검증 가능한 구현을 유지함.
- 요구나 실패 조건으로 설명할 수 없는 기능, 추상화, 설정, 의존성과 인프라를 추가하지 않음. 미래 확장 가능성만을 근거로 선제 도입하지 않음.
- 추가 복잡도가 필요할 때만 해결할 요구/실패 조건과 더 단순한 안으로 충족할 수 없는 이유를 짧게 설명함. 같은 설명과 검토를 형식적으로 반복하지 않음.
- 변경 목표와 무관한 리팩터링, 공통화와 전면 개편은 수행하지 않음.
- 단순화를 이유로 실제로 필요한 입력 검증, 오류 복구, 권한 처리와 필수 검증을 제거하지 않음.
- 수용 기준과 변경 영향 검증을 충족하면 새로운 기능 확장과 정리 작업을 시작하지 않고 결과와 남은 한계를 반환함.

## 도구와 정보 경계

- 제공 모델, 인증과 관리 설정을 유지함. 도구 업데이트, 개인 키와 외부 모델로 제한을 우회하지 않음.
- 과제 자료, 코드와 결과를 외부 서비스에 업로드하지 않음.
- 환경변수 전체, 인증 파일과 비밀값을 출력하지 않음. 보안 검토는 값 대신 필요한 위치와 경계를 기록함.
- Computer Use는 사용하지 않음. Chrome DevTools MCP(Model Context Protocol: 모델과 도구의 연결 규약)를 이용한 본인 앱 검증과 일괄 동일시하지 않음.
- qa-ui가 실제 사용 가능한 경우 본인 앱의 UI(User Interface: 화면과 조작 기능), 콘솔과 요청을 검증함. 미지원이면 수동 미리보기와 명령 검사로 전환함.
- 응시 플랫폼, 감독, 신분증, 제출과 후속 서술형 화면은 자동 조작하거나 캡처하지 않음.

## 검증과 실패 증거

- 중요한 예상 결과는 원문과 실제 답변에서 정하고 작은 입력으로 먼저 검산함. 구현 결과나 같은 처리 함수로 예상값을 역산하지 않음.
- 해당 기능의 목록, 건수와 내보내기 범위를 같은 기준으로 대조하고 빈 결과 뒤 복구도 확인함.
- 기대값 완화, 검사 삭제나 건너뛰기로 통과시키지 않음. 제품 결함, 잘못된 검사 조건과 환경 문제를 구분하고 검사 중 대상 상태가 바뀌면 영향받는 결과를 다시 확인함.

- 수용 기준의 예상과 실제를 비교함. 기대한 오류 응답은 검증 성공일 수 있으므로 상태 코드만으로 결함을 단정하지 않음.
- 구현됨, 검증 통과, 실제 실패와 미실행을 구분함. 명령을 적거나 도구를 호출한 사실만으로 통과라고 표시하지 않음.
- 실제 UI 실패는 수정, 새로고침과 상태 초기화 전에 본인 앱의 실패 화면, 재현 입력/상태, 예상/실제와 콘솔/요청 오류를 보존함.
- 명령 실패는 실행 명령, 작업 위치, 종료 코드와 원문 출력을 보존함. 의미 없는 화면 캡처로 대신하지 않음.
- 시작할 때 확인한 허용 증거 위치를 사용함. 비밀값이나 감독 화면이 섞이면 안전한 범위로 제한함. 수집이 불가능하면 사유와 대체 근거를 보고함.
- 캡처나 기록 도구의 실패를 앱 결함과 분리하고 즉시 알림. 증거 생성 실패가 다른 독립 작업까지 자동 중단시키지는 않음.
- 같은 실패는 식별자를 유지하고 수정과 재검증을 연결함. 원본 실패를 성공 결과로 덮거나 삭제하지 않음.
- 통과한 검사마다 증거 파일과 화면을 쌓지 않음. 실패 수정 뒤 같은 조건과 영향받는 흐름을 다시 확인함.
- 실제 재현, 코드에 근거한 위험 후보와 미검증을 구분함. 검사 미실행을 보안 결함 없음으로 표현하지 않음.

## 역할과 종료

- 메인이 요구 판단, 구현 통합과 검토 결과 채택을 책임짐. 검토 역할은 파일을 수정하지 않음.
- 위임 요청이 있을 때만 범위가 독립적인 작업을 분리함. 구현을 맡기면 소유 파일과 입출력 계약을 명시하고 공유 설정과 테스트 상태의 동시 수정을 피함.
- 역할 미지원은 같은 요청문의 순차 수행으로 대체하고 실제 독립 검토와 구분함.
- 제출물 확정 전에 모든 수정 주체를 종료하고 저장, 필수 파일, 실제 검사와 한계를 확인함.
- 최종 제출 확인은 사람이 수행함. 후속 서술형 단계에서는 AI와 복사/붙여넣기를 사용하지 않음.
