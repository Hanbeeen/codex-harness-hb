# UI 검토 기준

UI(User Interface: 화면과 조작 기능)의 실제 요구 위반과 작업 실패를 찾는 기준임. 공식 채점표와 자동 점수 계산표가 아님. 사람이 원문과 수용 기준을 확정하고, 검토자는 관찰한 결과, 코드로 찾은 위험과 미검증을 나눠 반환함.

## 입력과 판정

검토 전에 요구 원문, 허용 본인 앱 주소/화면, 코드와 데이터 상태, 예상 결과가 있는 TC(Test Case: 검증 사례), 허용 증거 위치와 호출 예산을 받음. 없는 값은 만들지 않음. 정적 검토는 코드와 문서를 읽는 검사이고 실행 검증은 앱을 조작하는 검사임.

| 판정 | 기록 기준 |
|:---|:---|
| pass | 지정 조건에서 실제 관찰한 결과가 수용 기준에 맞음 |
| fail | 재현한 조작과 실제 결과가 수용 기준을 위반함 |
| skipped | 실행하지 못했거나 필요한 조건/도구가 없어 관찰하지 못함 |
| 정적 위험 후보 | 파일:라인과 실패 가능 조건이 있으나 실제 재현은 하지 않았음 |
| 제안 | 현재 요구 위반을 입증하지 않은 개선 판단. 사람이 채택 여부를 결정함 |

코드에 처리 구문이 있다는 사실만으로 실행 사례를 pass로 표시하지 않음. 실제 실패를 관찰했다면 코드 위치가 불명확해도 위치 미확인으로 남김. 예상한 오류 응답은 정상 검증 결과일 수 있으므로 상태 코드만으로 결함을 단정하지 않음.

## 우선순위

| 먼저 확인할 대상 | 통과를 판단할 관찰 | 실패 또는 위험 사례 |
|:---|:---|:---|
| 필수 흐름 | 실제 입력에서 요구한 결과 확인까지 연결됨 | 버튼이 예시 성공만 표시하거나 필수 출력에 도달하지 못함 |
| 데이터 일치 | 원본, 필터/검색, 건수, 합계와 상세의 기준이 같음 | 이전 상세, 장식 수치와 잘못된 합계가 현재 결과에 섞임 |
| 보존과 복구 | 실패 뒤 입력과 이전 정상 데이터가 정한 계약대로 유지됨 | 오류를 숨기고 예시로 대체하거나 일부 데이터만 조용히 반영됨 |
| 작업 상태 | 현재 처리, 완료 범위와 다음 행동을 식별할 수 있음 | 실행 버튼이 계속 잠기거나 '적용'을 서버 저장으로 표시함 |
| 정보 순서 | 현재 조건, 주 동작과 결과를 찾을 수 있음 | 장식/설명이 필수 조작을 밀거나 주 동작이 서로 경쟁함 |
| 접근성과 내용 변화 | 키보드, 보이는 포커스, 작은 화면과 긴 값으로 필수 작업 가능 | 마우스 없이는 접근하지 못하거나 중요한 값/버튼이 가려짐 |
| 변경 범위 | 선택한 개선이 저장, 권한과 업무 규칙을 임의 변경하지 않음 | UI 정리 명목으로 데이터 계약이나 의존성을 바꿈 |

필수 흐름 실패, 잘못된 결과와 데이터 소실을 먼저 반환함. 색이나 카드 모양의 취향 차이와 후속 개선은 분리함.

## 정보 순서와 점진적 공개

- 첫 화면에서 해야 할 작업, 현재 조건과 주 동작을 식별할 수 있는지 확인함. 긴 제품 소개가 필요한지는 실제 사용 목적을 기준으로 판단함.
- 보조 설정과 긴 상세를 펼침 영역에 둘 수 있으나 필수 입력, 현재 적용 조건, 오류와 완료 범위를 숨기지 않음.
- 핵심 정보를 확인하려고 모든 카드를 열어야 하거나 필수 작업을 위해 여러 탭을 왕복해야 하는지 관찰함.
- 비교가 필요한 값은 같은 기준, 단위와 정렬을 사용함. 설명을 줄이려고 사실과 상태까지 제거하지 않음.
- 같은 행동은 버튼, 처리 중 문구와 완료 메시지에서 같은 의미로 표현함. 검색, 적용, 저장과 삭제의 범위를 혼용하지 않음.

## 상태별 실행 사례

아래 상태를 앱마다 전부 추가하는 목록으로 쓰지 않음. 해당 흐름에 존재하는 상태만 선택하고 제외 이유를 적음.

| 상태/전이 | 지정할 입력과 조작 | 기대할 관찰 |
|:---|:---|:---|
| 초기 | 처리 전 처음 진입 | 시작 방법과 예시 여부가 보이며 처리 완료를 꾸미지 않음 |
| 처리 중 | 실제 비동기 작업 실행 | 무엇을 기다리는지 보이고 필요한 중복 실행 제한이 적용됨 |
| 성공 | 정상 입력 처리 종료 | 실제 결과와 완료 범위가 보이고 필요한 다음 행동 가능 |
| 원본 없음 | 원본 항목이 없는 데이터 사용 | 검색 조건 문제와 구분하고 데이터 입력/확보 안내 표시 |
| 조건 불일치 | 원본이 있으나 일치하지 않는 조건 적용 | 원본을 지우지 않고 현재 조건과 변경/초기화 방법 표시 |
| 잘못된 입력 | 형식 또는 업무 규칙을 위반한 값 제출 | 고칠 위치와 이유가 보이고 입력/정상 데이터가 계약대로 보존됨 |
| 처리 실패 | 허용된 테스트 조건에서 실패 유발 | 실패 범위, 재시도 가능 여부와 이전 데이터의 상태를 식별 가능 |
| 복구 | 잘못된 값을 고치거나 허용된 재시도 수행 | 오류가 해소되고 실행 가능 상태로 돌아오며 이전 오류가 성공을 가리지 않음 |
| 새로고침/재시작 | 보존 계약이 있는 경우에만 수행 | 약속한 보존 범위와 안내가 실제 결과에 맞음 |

서버 응답 지연, 실패 주입이나 재시작을 위한 설정 변경 권한이 없으면 임의로 만들지 않고 해당 사례를 skipped로 남김.

## 비동기 응답과 숫자 일치

| 사례 | 조작/사전 조건 | 기대할 관찰 |
|:---|:---|:---|
| 늦게 도착한 이전 응답 | 조건 A 조회 직후 조건 B 조회, 가능하면 A가 더 늦게 완료되는 조건 사용 | 현재 조건 B의 결과가 유지되고 A가 덮지 않음 |
| 중복 실행 | 처리가 진행되는 동안 주 동작 반복 | 중복 반영 여부가 정한 계약에 맞고 버튼/결과가 복구 가능 |
| 목록과 건수 | 전체 목록에 필터, 검색과 페이지 이동 적용 | 전체 건수, 조건에 맞는 건수와 현재 페이지 건수의 표시 의미가 일관됨 |
| 합계와 단위 | 알려진 테스트 데이터에 조건 적용 | 현재 기준에 맞는 합계와 단위가 표시되고 분모/포함 범위가 식별 가능 |
| 선택과 상세 | 항목 선택 후 필터로 제외하거나 데이터를 교체 | 선택을 유지/해제하는 계약에 맞고 다른 항목의 상세로 혼동하지 않음 |
| 빈 결과 전환 | 정상 결과에서 조건 불일치로 바꾼 뒤 조건 복구 | 이전 값이 빈 결과에 남지 않고 복구 후 실제 결과와 맞음 |

응답 순서가 달라질 수 있다는 근거는 [React 공식 문서](https://react.dev/reference/react/useEffect)에 있음. 특정 React 코드 모양을 통과 조건으로 삼지 않음. 순서를 바꿀 수 없는 환경에서는 정적 위험 검토와 실제 재현 여부를 구분함. 측정하지 않은 시간과 성능 향상률을 적지 않음.

## 접근성과 작은 화면

- 입력에는 접근 가능한 이름이 있고 의미와 연결돼야 함. placeholder(입력 전 예시 문구)만으로 레이블을 대신하지 않음.
- 키보드만으로 필수 입력, 주 동작, 결과와 복구 동작에 도달함. 포커스가 보이고 고정 헤더, 푸터와 겹침 영역에 가려지지 않는지 확인함.
- 대화상자가 있으면 열기, 내부 이동, 닫기와 닫은 뒤 포커스 복귀를 확인함. 펼침/선택 상태가 있다면 현재 상태를 알 수 있어야 함. 없는 컴포넌트를 검사를 위해 새로 추가하지 않음.
- 상태와 오류를 색만으로 구분하지 않음. 아이콘만 있는 버튼의 이름과 장식 아이콘의 보조기술 노출 여부를 확인함.
- 처리 완료, 결과 변경과 오류의 보조기술 전달은 코드와 실제 검사를 구분함. 스크린리더(화면 내용을 음성으로 읽는 보조기술)를 실행하지 않았다면 적합성을 단언하지 않음.
- 좁은 화면과 긴 값에서 필수 정보와 조작이 유지되는지 확인함. 표처럼 양방향 배치가 필요한 영역과 페이지 전체의 불필요한 가로 넘침을 구분함.
- 수치 기준이 필요하면 기준과 실제 측정 방법을 함께 기록함. W3C Reflow 해설의 세로 스크롤 콘텐츠 기준은 폭 320 CSS 픽셀이며 의미상 양방향 배치가 필요한 영역은 예외를 구분함. 이 검사만으로 접근성 전체 적합을 주장하지 않음. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- 모션이 있다면 줄인 모션 설정에서 필수 조작과 상태 정보가 유지되는지 확인함. 불필요한 애니메이션 추가를 검토 완료 기준으로 삼지 않음.

레이블, 의미 있는 기본 HTML 요소, 포커스, 폼과 상태 검토의 참고 원본: [Vercel 고정 규칙](https://github.com/vercel-labs/web-interface-guidelines/blob/434b7f91364665f2f733b310ec54809bf8f37937/command.md). 원문을 읽은 사실과 실제 키보드/화면 검사를 완료한 사실은 다름.

## 실행 도구와 인계

Computer Use는 사용하지 않음. Chrome DevTools MCP(Model Context Protocol: 모델과 도구의 연결 규약)를 이용한 본인 앱 검증을 일괄 금지된 작업으로 취급하지 않음. 실제 제공된 도구, 주소와 권한을 확인한 범위에서만 사용함. 시험 플랫폼, 감독, 신분증, 제출과 후속 서술형 화면은 열거나 조작하거나 캡처하지 않음.

| 실행 조건 | 반환할 결과 |
|:---|:---|
| 허용된 qa-ui 도구와 실행 중 본인 앱이 있음 | 지정 사례의 화면, 콘솔과 요청을 관찰하고 예상/실제 반환 |
| 도구 없음 또는 앱 실행 안 됨 | 해당 사례를 skipped로 남기고 설치/설정 변경 없이 대체 관찰 제시 |
| 실제 UI 실패 관찰 | 수정, 새로고침과 초기화 전에 허용된 실패 화면과 재현 입력/상태, 예상/실제 및 오류 보존 |
| 캡처나 기록 도구 실패 | 즉시 원문 오류와 미수집 항목 보고. 앱 결함과 분리하고 독립 관찰은 가능한 범위에서 지속 |
| 코드/데이터가 검사 도중 바뀜 | 영향받은 이전 결과를 현재 상태의 pass로 재사용하지 않고 재검증 조건 지정 |
| 수동 미리보기로 대체 | 사람이 관찰한 범위를 표시하고 명령 검사 성공을 화면 조작 성공으로 확대하지 않음 |

실패 증거는 [qa-ui 역할](../roles/qa-ui.md)의 계약과 지정한 허용 위치를 따름. 통과 화면을 매번 파일로 쌓지 않음. 재현한 실패, 정적 위험, 제안과 미검증을 [인계 양식](qa-handoff.md)에 연결함.

이 문서는 검토 기준이며 이번 준비 작업에서 실제 브라우저, 자동 스킬 등록과 앱 실행 검증을 수행했다는 기록이 아님.
