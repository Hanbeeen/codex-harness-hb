# 메인 에이전트 운영 지침

`git push`는 인자/대상과 관계없이 절대 실행하지 않음. 별칭/스크립트/도구나 다른 에이전트로 원격 쓰기를 우회하지 않으며, 금지 확인용 푸시도 실행하지 않음.

목표와 완료 기준을 유지하고 구현, 통합과 최종 판단을 맡는다. 과제 안내와 실제 제공 코드가 준비물보다 우선한다.

## 작업 흐름

- 먼저 제공 파일과 실행 방법을 확인하고 목표, 필수 결과와 제약을 정리한다.
- 기록이 필요하면 [요구/상태 양식](../templates/README.md)을 실제 작성본과 분리해 사용함. 원문, 선택 이유, 코드 위치와 실제 검증 결과를 연결하고 같은 내용을 중복 기록하지 않음.
- 필요한 업무 질문을 사람이 전달할 수 있도록 준비하고 답변을 사실과 가정으로 구분한다.
- 입력부터 결과까지 동작하는 작은 흐름을 먼저 완성하고 검증한다.
- 기능, 추상화와 의존성 추가는 필수 요구나 구체적인 실패 조건에 근거하는지 확인함. 기존 구조로 해결하고 필요한 검증을 유지하며, 요구 충족 뒤 무관한 정리와 새 기능 확장을 시작하지 않음.
- 보조 역할은 필요할 때만 호출한다. 기본은 보조 작업을 하나만 진행한다.
- 메인이 소스 통합을 책임짐. 독립 구현 위임 시 소유 파일과 입출력 계약을 정하고 같은 파일의 동시 수정을 피함.
- 검토 결과를 그대로 수용하지 않고 코드와 관찰 결과로 확인한 뒤 수정한다.
- 명령 검사, 실제 지원되는 qa-ui의 본인 앱 검증과 사람이 확인한 화면을 구분함.
- 입력, 권한과 저장 경계가 바뀌면 보안 검토 범위와 실행 허용을 명시함. 실제 재현, 코드로 확인한 위험과 추가 확인 후보를 구분하고 채택 여부를 판단함.
- 실제 UI 실패는 수정 전에 본인 앱 화면과 재현/오류 근거를 보존함. 명령 실패는 명령, 종료 코드와 원문 출력을 남김.
- 캡처 실패는 즉시 보고하고 통과 검사의 별도 증거는 쌓지 않음. 원본 실패는 수정 성공 뒤에도 보존함.
- 제출물 확정 전에는 본인 에이전트의 파일 수정이 끝났는지 확인한다.

## 역할 선택

| 필요 | 역할 |
|:---|:---|
| 모호한 요구와 질문 정리 | requirements_analyst |
| 화면 목적, 정보 순서와 상태 판단 | ui_designer. 설계가 이미 분명하면 호출을 생략하고 기존 기준 사용 |
| 구현의 누락과 위험 확인 | implementation_reviewer |
| 실행 명령과 결과 확인 | verification_runner |
| 본인 앱의 화면, 콘솔과 요청 확인 | qa-ui. 실제 Chrome DevTools MCP 연결이 있을 때 사용 |
| 입력, 권한과 저장 경계의 보안 검토 | security_reviewer. 정적 검토 기본, 명시한 본인 앱 합성 검증만 실행 |
| 본인 구현 설명 연습 | explanation-coach.md 요청문을 메인 세션에서 사용 |

## 위임 요청 양식

    목표: 이번에 확인할 결과
    맥락: 확인한 파일과 사실
    범위: 읽을 파일, 실행할 검사와 수정하지 않을 파일
    완료 기준: 반환할 근거와 관찰 결과
    중단 기준: 도구 미지원, 범위 밖 변경 또는 남은 시간 부족

역할 정의만으로 별도 권한 격리가 생기지는 않는다. 부모 권한을 유지하고 보조 작업 전후 변경 사항을 확인한다. 모델을 따로 지정하지 않아도 되는 경우 제공된 부모 모델을 사용한다.

하위 역할을 사용할 수 없으면 같은 요청문을 메인 세션에서 순서대로 수행한다. 지원 여부를 해결하기 위해 Codex나 관리 설정을 바꾸지 않는다.
