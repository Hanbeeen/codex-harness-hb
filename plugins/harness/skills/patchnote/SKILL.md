# /patchnote: 릴리스 패치노트 작성

이번 릴리스에 들어간 커밋을 읽고, 그 제품을 쓰는 사람이 읽을 패치노트를 만든다.
읽는 사람은 코드를 보지 않는다. 화면에서 무엇이 달라졌는지만 궁금하다.

산출물은 **대화창에 출력하는 텍스트 한 덩어리**다. 메신저/메일에 그대로 붙여넣는 용도.

## ⚠️ 절대 금지

- **파일을 만들지 않는다.** 저장, 커밋, push 어느 것도 하지 않는다. 화면 출력이 이 커맨드의 끝이다.
- **커밋에 없는 내용을 지어내지 않는다.** 근거가 되는 커밋이 없는 항목은 쓰지 않는다.
- **내부 식별자를 노출하지 않는다.** 함수명, 파일명, 모듈명, 스코프(`utils`, `import`), 라이브러리명은 패치노트에 나오면 안 된다.
- **em-dash(`—`), 물결표(`~`) 금지.** 범위는 하이픈(`30-40건`). 사용자 글로벌 표기 룰 그대로.
- 항목마다 이모지/굵게를 뿌리지 않는다. 섹션 제목만 구분되면 충분하다.

## 1) 완성 형태

```
v1.5.2 패치노트

개선
- 가져오기 결과 CSV 에 원본 행 번호, 파일명, 오류 사유 열 추가
- 가져오기 재시도 대기 30분에서 30초로 단축
- 가져오기 결과가 불완전하면 경고 배너로 알림

수정
- 일부 CSV/압축 파일이 가져오기에서 누락되던 문제
- 시트 이름 공백 처리로 가져오기가 실패하던 문제
- 가져오기 실패 사유가 잘못 표시되던 문제
- CSV 내보내기를 취소해도 파일이 저장되던 문제
```

### 섹션

| 섹션 | 담는 것 | 순서 |
|:---|:---|:---|
| 신규 | 없던 화면, 메뉴, 기능이 생긴 것 | 있으면 맨 위 |
| 개선 | 있던 기능이 더 좋아진 것. 항목/옵션 추가, 속도, 표시 개선 | 그다음 |
| 수정 | 잘못 돌던 것이 바로잡힌 것 | 마지막 |

**빈 섹션은 쓰지 않는다.** 대부분의 릴리스는 개선/수정 둘뿐이다. "신규" 를 채우려고 개선 항목을 끌어올리지 않는다.

## 2) 항목 도출: 네 단계

### 2-1. 범위 확정

인자로 버전이나 커밋 범위(`v1.5.1..HEAD`)를 받았으면 그대로 쓴다. 없으면 후보를 뽑아 **사용자에게 한 줄로 확인받고 시작한다.**

```bash
cat VERSION 2>/dev/null                 # 이번 버전 번호 (없으면 package.json version)
git log --oneline -5 -- VERSION         # VERSION 이 바뀐 지점 = 직전 릴리스 경계
git tag --sort=-creatordate | head -5   # 태그를 쓰는 레포면 이쪽이 더 정확
git log --oneline main..HEAD            # 릴리스 후보 브랜치에 쌓인 것
```

확인 한 줄 예: `v1.5.1 릴리스 커밋(3f9c2e10) 이후 13개 커밋을 범위로 잡았음. 이대로 진행할지?`

레포에 VERSION 도 태그도 없으면 `main..HEAD` 를 기본 후보로 제시한다.

**스쿼시된 배포 브랜치를 범위로 잡지 않는다.** 범위 안 커밋이 한두 개인데 `--stat` 의 변경 파일이 수십 개면, 릴리스 전체가 한 커밋으로 눌린 배포 커밋이다. 재료가 되는 개별 커밋이 없으니 그 작업이 실제로 쌓인 브랜치(대개 `main`)로 범위를 다시 잡는다.

### 2-2. 수집

범위 안의 **커밋 제목과 본문을 모두** 읽는다.

```bash
git log <범위> --no-merges --format="%h%n%s%n%b%n---"
```

`--no-merges` 는 반드시 붙인다. PR 머지 커밋(`Merged in feature/xxx (pull request #124)`)은 제목도 본문도 재료가 아닌데, 빼지 않으면 개수만 부풀려 병합 판단을 흐린다.

**본문 첫 단락이 가장 중요한 재료다.** `/commit` 규칙이 그 자리에 "왜 바꿨는지, 사용자에게 어떻게 보였는지" 를 쓰게 하고 있어서, 패치노트 문장이 거의 그대로 들어 있다. 제목은 구현을 말하고 본문은 증상을 말한다. 패치노트는 증상 쪽이다.

본문이 비었거나 구현 얘기뿐인 커밋만 `git show <해시> --stat` 으로 무엇이 바뀐 화면인지 확인한다. diff 전문을 읽을 일은 거의 없다.

### 2-3. 선별: 화면이 안 바뀌었으면 뺀다

각 커밋에 이 질문 하나를 던진다.

> **이 제품을 쓰는 사람이 화면에서 겪는 무엇이 달라졌나?**

한 문장으로 답이 나오면 남기고, 안 나오면 뺀다. 코드가 얼마나 많이 바뀌었는지는 기준이 아니다.

| 대개 빠지는 것 | 이유 |
|:---|:---|
| 버전 표기, 설정, 의존성, CI (`chore`, `build`, `ci`) | 릴리스 메타. 쓰는 사람과 무관 |
| 리팩터, 테스트, 포매팅 (`refactor`, `test`, `style`) | 화면 표면이 그대로 |
| 화면에 드러나지 않는 내부 강화 | 겪던 오류가 사라졌으면 그때만 넣음 |
| 이번 범위 안에서 만들고 이번 범위 안에서 고친 것 | 쓰는 사람은 중간 상태를 본 적이 없음. 최종 상태만 씀 |

마지막 줄이 가장 자주 놓치는 지점이다. 새 기능을 넣은 커밋과 그 기능의 후속 손질 커밋이 같은 릴리스에 있으면, 후속 손질은 **수정 항목이 아니라 그 기능 항목에 흡수**된다. 밖에서 보면 처음부터 그렇게 나온 기능이기 때문이다.

빠진 커밋은 **작업 후 한 줄로 보고**한다. 무엇을 왜 뺐는지 밝혀야 판단을 되돌릴 수 있다.

### 2-4. 병합: 겪은 불편이 같으면 한 줄

**커밋 하나가 항목 하나가 아니다.** 사용자가 겪은 불편이 같으면 커밋이 셋이어도 한 줄이다.

병합 기준은 원인이 아니라 증상이다. 원인이 전혀 다른 두 버그라도 겪는 쪽에서 `가져오기가 실패한다` 로 같으면 한 줄로 합친다. 반대로 같은 파일을 고쳤어도 겪는 증상이 다르면 나눈다.

합치고 나면 **항목 수가 커밋 수의 절반 근처**로 떨어지는 것이 보통이다. 10개를 넘으면 병합이 덜 된 것이니 다시 본다.

## 3) 번역: 내부 말을 화면 말로

읽는 사람은 코드에 쓰인 이름을 모른다. 자기가 화면에서 보는 말만 안다.

| 하는 일 | 예 |
|:---|:---|
| 코드 이름, 스코프, 파일명을 지운다 | `fix(utils) ... isImportDegraded` → 흔적 없음 |
| 내부 기능명을 화면 라벨로 바꾼다 | 임포트 잡 → 가져오기 |
| 아는 사람만 아는 규격명은 상위 개념으로 올린다 | RFC 4180, UTF-8 BOM, TSV → CSV 파일 |
| 구현이 아니라 결과를 쓴다 | 진단 저장 → 경고 배너로 알림 |

**화면 라벨을 지어내지 않는다.** 그 기능을 화면에서 뭐라고 부르는지 모르면 프론트 소스에서 실제 문구를 찾는다.

```bash
grep -rn "가져오기\|임포트" frontend/src/views --include=*.vue | head -20
```

찾아도 확실하지 않으면 그 항목만 후보 두 개를 달아 사용자에게 묻는다. 틀린 라벨은 안 쓴 것보다 나쁘다. 공지를 받은 사람이 화면에서 그 말을 못 찾기 때문이다.

## 4) 문체

| 섹션 | 종결 | 예 |
|:---|:---|:---|
| 신규/개선 | 명사형 | `열 추가` / `30초로 단축` / `경고 배너로 알림` |
| 수정 | 증상 + `던 문제` | `누락되던 문제` / `실패하던 문제` / `저장되던 문제` |

- **한 항목은 한 줄.** 30-45자 근처. 두 줄로 접히면 내용이 두 개 섞인 것이니 쪼개거나 줄인다.
- **수치는 구체적으로.** `재시도 대기 단축` 이 아니라 `30분에서 30초로 단축`. 숫자가 체감을 만든다.
- **원인을 쓰지 않는다.** `UTF-8 BOM 때문에 파싱이 실패해서` 는 읽는 사람의 관심 밖이다. 무엇이 안 됐고 이제 되는지만 쓴다.
- **수정 항목은 과거형 증상으로 끝낸다.** `고쳤음` 을 붙이지 않는다. 수정 섹션에 있다는 것이 이미 고쳤다는 뜻이다.
- 완결형 종결(`-했습니다`, `-합니다`)을 쓰지 않는다. 사용자 글로벌 개조식 룰 그대로.

## 5) 모범 예시: v1.5.2 매핑

커밋 13개가 항목 7개가 되는 과정 전부. 실제 릴리스의 판정을 그대로 두고 도메인만 CSV 가져오기 서비스로 바꾼 예시다. **이 표의 판정 방식을 그대로 가져다 쓴다.**

| 커밋 | 결과 | 판정 |
|:---|:---|:---|
| feat(reports) 가져오기 결과 CSV 에 원본 행 번호, 파일명, 오류 사유 열 추가 | 개선 1 | 제목이 이미 체감 서술이라 거의 그대로 |
| fix(utils) 결과 CSV 부가 열을 내보내기 CSV 와 같은 구성으로 | 개선 1 에 흡수 | 같은 릴리스 안 후속 손질. 밖에서는 한 기능 |
| feat(import) 가져오기 재시도 대기 30분에서 30초로 | 개선 2 | 수치를 살리고 `단축` 만 붙임 |
| feat(import) 가져오기 진단 저장과 불완전 결과 경고 | 개선 3 | 제목은 구현. 본문 증상을 뒤집어 씀 |
| fix(import) UTF-8 BOM 이 붙은 CSV 판별 복구 | 수정 1 | 아래와 병합 |
| fix(import) 업로드 폴더 권한과 링크 정리 복구 | 수정 1 | 원인은 다르나 겪는 증상이 `파일이 가져오기에서 빠짐` 으로 같음 |
| fix(sheets) 위험한 공백이 든 시트 이름을 저장 전 차단 | 수정 2 | 아래와 병합 |
| fix(sheets) 이름 게이트와 정규화의 문자 집합 정정 | 수정 2 | 같은 증상의 보완 |
| fix(import) 가져오기 실패 사유가 엉뚱한 원인을 가리키던 것 | 수정 3 | 아래와 병합 |
| fix(import) 실패 워커와 빈 결과 진단 정정 | 수정 3 | 같은 증상 |
| fix(ui) 중단한 CSV 내보내기가 파일까지 내려주던 것 | 수정 4 | 그대로 |
| fix(security) 빈 예외 처리 블록에 처리 내용 명시 | 제외 | 화면에 드러나는 변화 없음 |
| chore(release) 버전 표기 1.5.2 로 갱신 | 제외 | 릴리스 메타 |

### 본문이 문장이 되는 과정

커밋 `feat(import): 가져오기 진단 저장과 불완전 결과 경고` 의 본문:

```
워커가 죽어 가져온 행이 0건이어도 화면이 '완료' 로만 보여
가져오기가 성공한 것으로 오인되던 문제였음.

- 확정 시점 워커 상태/행 수를 진단으로 저장(lastImportDiag)
- 불완전 판정과 빈 결과 문구를 상세 화면 경고로 분기(isImportDegraded)
```

여기서 쓰는 것은 첫 단락뿐이다. `화면이 완료 로만 보여 오인되던` 을 뒤집으면 `불완전하면 경고로 알림` 이 된다. bullet 의 `lastImportDiag`, `isImportDegraded` 는 구현이라 전부 버린다. 제목의 `진단 저장` 도 마찬가지다.

결과: **가져오기 결과가 불완전하면 경고 배너로 알림**

## 6) 동작 절차

1. **범위 확정** (2-1). 인자가 없으면 후보를 제시하고 한 줄 확인받는다.
2. **수집** (2-2). 제목과 본문을 전부 읽는다.
3. **선별/병합표 작성** (2-3, 2-4). 5) 모범 예시와 같은 표를 만든다. 이 표가 판단의 근거다.
4. **번역/문체 적용** (3, 4). 화면 라벨이 불확실하면 소스에서 확인한다.
5. **자기 점검** (아래 7).
6. **출력**: 패치노트 본문 → 선별/병합표 → 제외 커밋 한 줄 보고 순으로 낸다.

사용자가 인자로 준 메모(`--강조: 재시도 대기 위주로` 같은)가 있으면 항목 순서나 표현에 반영한다.

## 7) 자기 점검 (출력 직전)

| 확인 | 걸리면 |
|:---|:---|
| 항목이 10개를 넘나 | 병합이 덜 됐다. 증상이 같은 것을 다시 묶는다 |
| 코드 이름, 파일명, 스코프가 남았나 | 지우고 화면 말로 바꾼다 |
| 두 줄로 접히는 항목이 있나 | 내용이 둘이다. 쪼개거나 줄인다 |
| 원인을 설명하는 항목이 있나 | 증상과 결과만 남긴다 |
| `—` 또는 `~` 가 있나 | 하이픈/괄호로 바꾼다 |
| 완결형(`-합니다`, `-했습니다`)이 있나 | 명사형, `던 문제` 로 바꾼다 |
| 커밋 근거가 없는 항목이 있나 | 지운다 |
| 파일을 만들었나 | 만들면 안 된다. 화면 출력만 |
