# /commit: 컨벤션 커밋 메시지 자동 작성/실행

스테이지/미스테이지 변경을 진단해 다음 형식으로 메시지를 자동 작성한 뒤 `git commit` 실행. 사용자가 인자로 추가 메모를 주면 본문에 자연스럽게 반영.

## ⚠️ 절대 금지

- **`git push` 절대 실행하지 말 것.** push 는 사용자가 직접 수행. 이 skill 의 범위는
  `git commit` 까지로 한정. 사용자가 명시적으로 "push 까지", "푸시해줘" 같은
  지시를 같은 메시지에서 주지 않는 한 push 시도 금지.
- 사용자가 push 를 함께 원할 가능성이 있다고 짐작해서 `&&` / 별도 step 으로
  엮어 실행하지 않음. commit 종료 후 "이제 push 까지 진행할까?" 같은 임의 제안도
  금지: 사용자가 다음 지시로 명시할 때까지 대기.
- **`Co-Authored-By:` 라인 절대 넣지 말 것.** Claude / Anthropic / AI 관련 어떤 형태의 trailer도 추가 X.
- **🤖 Generated with [Claude Code] 같은 footer 절대 넣지 말 것.**
- **사용자가 명시 요청하지 않은 모든 AI 표시, 서명, attribution 추가 금지.**
- 커밋 메시지는 사용자가 직접 쓴 것처럼 깔끔히 끝나야 함.

## ⚠️ 한 commit에 한 기능만: 무조건 기능별 commit

사용자 글로벌 워크플로우 룰(`~/.codex/AGENTS.md`). **이 skill을 호출할 때마다 다음을 우선 검토.**

- **변경에 두 개 이상의 의도가 섞여 있으면 commit을 둘로 쪼갠다.** 예: (A) 버그 fix + (B) 새 인터랙션 추가가 한 워킹 디렉토리에 같이 있으면 A만 stage, commit → B만 stage, commit 순서. 한 commit에 절대 묶지 않는다.
- **한 사용자 메시지에 여러 기능 요청이 와도 각각 별도 commit으로 분리.** 작업 흐름이 같다는 것이 commit을 묶을 정당성이 되지 않는다.
- **단일 의미 단위로 묶을 수 있는 경우만 한 commit**: 같은 버그의 코드 + 테스트 + 문서가 한 셋트인 경우. 다른 의도면 분리.
- 변경이 이미 한 묶음으로 stage되어 분리하기 어려우면 `git reset HEAD <path>`로 부분 unstage 후 진행.
- 분리가 정말 어려우면 사용자에게 한 줄 보고: "변경 N건이 분리 가능: 별도 N개 commit으로 진행할지, 한 묶음으로 진행할지 선택?"

## 0) 커밋 전 흡수 판단 (별도 commit vs 앞선 commit에 흡수)

커밋하기 **전에**, 이번 변경이 **이 브랜치의 앞선 커밋 중 하나에 흡수돼야 하는지** 먼저 판단한다. 같은 "기능"에 대한 후속 손질(앞서 만든 UI, 기능을 정렬, 레이아웃 변경, 사소한 추가/수정 등: 별도 commit 내기 애매한 것)이면 그 기능 커밋에 흡수하고, 새 독립 기능이면 별도 commit 한다.

### 판단

- `git log <base>..HEAD --oneline`(+ 필요한 커밋 diff)로 앞선 커밋 확인. `<base>` = `git merge-base HEAD origin/main`(없으면 `main`). 앞선 커밋이 없으면(브랜치 첫 커밋) 바로 별도 commit.
- **흡수**: 이번 변경이 앞선 어떤 커밋이 만든 기능의 **후속 손질**(같은 기능 범주, 별도 낼 만큼 독립적이지 않음) → 그 커밋에 흡수.
- **별도**: 새 기능/새 의미 단위 → 별도 commit(아래 1) 이후 일반 절차).
- 애매하면 사용자에게 한 줄 확인: "이 변경, `<앞선커밋 요약>`에 흡수할지 별도 commit할지?".

### 흡수하는 경우

- **대상이 HEAD(직전 커밋)면**: 해당 파일만 stage 후 `git commit --amend`. replay 없어 가장 안전. 메시지는 최종 상태 기준으로 유지(대부분)하거나, 기능이 늘면 갱신.
- **대상이 더 앞선 커밋이면**: `git commit --fixup=<대상>`(메시지 유지) 또는 `--fixup=amend:<대상>`(메시지 갱신) 후 `GIT_SEQUENCE_EDITOR=true GIT_EDITOR=true git rebase -i --autosquash <base>`.
  - autosquash 전 워킹트리의 **다른 미스테이지 변경은 `git stash`** 후 rebase, 끝나면 복원. 충돌로 abort 한 경우에도 stash 를 복원한 뒤 멈춘다.
  - history rewrite 다. rebase 전에 백업 ref 를 만든다(`git update-ref refs/backup/commit-<날짜시각> HEAD`). 충돌이 나면 `git rebase --abort` 로 원상 복구하고 멈춰서 알린다. 대상 커밋이 이미 push 됐으면 force-push 가 필요하다고 먼저 경고하고 확인을 받는다.
- 흡수 후 `git diff` 정합성(최종 내용 보존) 확인. 흡수가 끝나면 이 커밋 작업은 종료: 아래 메시지 작성 절차는 건너뛴다(대상 커밋 메시지를 쓰는 것).

## 0.5) 커밋 전 경량 검증 (리뷰 에이전트 1개)

커밋(또는 흡수) 실행 **전에**, 이번에 커밋할 변경분(diff)을 **리뷰 에이전트 1개가 네 렌즈로 한 번에** 점검하고, 나온 발견 중 안전한 것을 반영한 뒤 커밋함. 커밋마다 부담 없이 도는 것이 목적이라 보안 점검/런타임 QA 는 여기서 안 함.

### 방식

- **리뷰 에이전트 1개를 아래 값 그대로 호출**. 렌즈별로 에이전트를 나누지 않음.
    - Claude Code: Agent 도구에 `subagent_type: "Explore"`, `model: "haiku"`, `effort: "low"`. Explore 는 읽기 전용이고 CLAUDE.md, 메모리를 싣지 않아 시작 컨텍스트가 작음(2026-10-21 측정: general-purpose 약 75K 토큰, Explore 약 29K). effort 를 지정하지 않으면 Haiku 5.5 가 thinking 을 길게 써서 리뷰 1건에 4-8분 걸렸음(2026-10-21 측정)
    - Codex: 읽기 전용 서브에이전트를 가장 가벼운 모델과 낮은 effort 로 띄움. 서브에이전트를 띄울 수 없는 환경이면 메인이 같은 네 렌즈와 출력 형식으로 직접 점검
- **diff 는 파일로 넘김**: 커밋 대상 diff 를 임시 폴더(scratchpad 가 있으면 그곳)에 저장하고(`git diff --cached`, staged 가 없으면 `git diff HEAD -- <커밋할 파일들>`) 그 경로를 프롬프트에 넣음. 작업 디렉터리, staged/미스테이지 혼동을 막고 에이전트의 git 호출을 줄임.
- **프롬프트에 담을 것**: diff 파일 경로, 레포 루트, 변경 요지 1-2줄, 아래 네 렌즈, 범위 제한(diff 먼저, 확인이 필요할 때만 관련 파일 읽기, 저장소 전체 스캔 금지, 도구 호출 8회 이내), 출력 형식.
- **출력 형식**: 발견마다 `파일:라인 | 렌즈 | 문제 | 구체적 비용 | 제안 한 줄`, 중요도 순 최대 5건. 확신이 낮으면 (불확실) 표시. 발견 없으면 "없음" 한 줄.
- 결과가 오면 **메인(=`/commit` 실행 주체)이 안전한 것만 직접 수정** 후 커밋.

### 네 렌즈 (에이전트 1개가 모두 봄)

- **재사용(Code Reuse)**: 기존 유틸리티, 헬퍼로 대체 가능한 새 코드 / 기존 기능과 중복되는 새 함수 / 기존 유틸을 쓸 수 있는 인라인 로직.
- **품질(Code Quality)**: 중복 상태, 파라미터 스프롤(parameter sprawl: 함수 인자가 계속 늘어나 관리가 어려워짐), 복붙 패턴 / 추상화 누수(leaky abstraction: 감췄어야 할 내부 구현이 밖으로 새어 나옴), stringly-typed(문자열로 타입을 대신하는 코드) / 불필요한 중첩.
- **효율(Efficiency)**: 불필요한 작업, 동시성 누락(병렬로 돌릴 수 있는 걸 순차 처리), 핫패스(hot path: 자주 실행되는 경로) 비대화 / 메모리 이슈, 과도한 연산.
- **성능 영향/사이드이펙트(Performance Impact & Side Effect)**:
    - 성능 영향: 기존 핫패스/루프에 추가된 비용, 새 I/O, 네트워크, DB 호출, 블로킹 연산, 시간/공간 복잡도 증가, 캐시 무효화(cache invalidation).
    - 사이드이펙트: 공유/전역 상태 변경, 기존 동작 변경, 이 코드에 의존하는 다른 모듈에 미치는 영향, API/시그니처 호환성 깨짐, 예상치 못한 부작용(로깅, 이벤트, 트랜잭션 등).

### 수정 적용 기준

- **범위 안에서 안전하게 고칠 수 있는 것**만 직접 수정(재사용 치환, 중복 제거, 사소한 정리 등).
- **동작 변경, 설계 판단, 범위 확장**을 요하거나 발견이 불확실하면 자동 수정 말고 **제안으로만 보고 + 사용자 확인**.
- 원래 요구사항 범위를 벗어난 **대규모 리팩터는 적용 금지**, 제안만(범위 보존). 수정으로 diff 가 바뀌면 그 최종 상태로 커밋.

### 생략

- 변경이 `*.md`, `docs/*` 만이거나 순수 `chore`(설정, 로깅, .gitignore)면 **검증 생략**(볼 코드 없음). 코드가 섞이면 실행.
- **실행 로직이 그대로인 코드 변경**도 생략: UI 문구/라벨, CSS/스타일 값, 주석, 포매팅만 바뀐 경우. 조건식, 분기, 호출, 데이터 처리가 한 줄이라도 바뀌면 크기와 무관하게 실행.
    - 줄 수 기준을 두지 않는 이유: 2026-10-21 `install.sh` 의 +3/-2 줄 변경에서 리뷰가 기존 설정 파일을 덮어쓸 수 있는 경로를 찾았음. 작은 변경이라서 안전한 것은 아님.
- 인자에 `--no-verify-agents` 면 이 검증을 건너뜀.

## 1) 메시지 형식

```
<type>(<scope>): <한 줄 요약: 한국어 개조식, 60자 이내, period 없음>

<배경/맥락 한 단락(1-3줄): 왜 바꿨는지, 무엇을 해결하는지. 명사형, 음슴체
혼용(완결형 "-했다/-한다" 만 금지). 직전 작업의 후속이면 그 관계도 명시.>

- <세부 변경 항목 1: 명사형 종결, 핵심만>
- <항목 2: 표기 변환/매핑은 `옛 → 새` 화살표로>
- <항목 3>
...
```

**메시지 끝은 마지막 bullet**(맨 위 절대 금지 참조).

### 형식 가드

- **첫 줄**: `<type>(<scope>): <한국어 요약>`. 60자 권장. 마침표 없음.
  `<scope>`는 **필수**: 이번 변경에서 주로 다룬 대상(디렉토리, 모듈, 기능 영역). 예: `utils`, `ui`, `api`, `auth`, `import`. 여러 영역이면 가장 중심 하나. 한 대상으로 도저히 못 좁히는 드문 경우만 생략.
- **본문 첫 단락**: 1-3줄로 변경 배경(왜/무엇 해결). **명사형/음슴체 혼용**: 완결형 서술 종결("-했다/-였다/-한다/-된다/-있었다") 만 금지(아래 7) 어투 규칙 참조).
- **bullet list**: `- ` 시작. 항목 끝은 명사형(-함/-됨/-임/명사). `**굵게**`는 강조 단어에만 절제 사용.
- **변환/매핑**: `옛 표기 → 새 표기` 화살표(`→` U+2192). 영문 enum → 한국어 라벨 같은 경우 자주 사용.
- **코드 식별자, 파일명, 라벨**: 백틱(`` ` ``) 감쌈. 예: `importer/cli.py`, `ImportJobPayload`, "검토 완료로 표시".
  **예외**: 6) 모범 예시처럼 항목 **끝 괄호**에 식별자를 몰아 적는 자리는 백틱 없이 맨 텍스트. `권한 복구(restoreDirPermissions)`. 문장 중간에 식별자가 오면 종전대로 백틱.
- **들여쓰기 보조 항목**: 같은 항목 안에서 예시/하위 항목은 4칸 들여쓰기.

## 2) 분량 상한 (IDE 잘림 방지)

분량은 변경의 정보량에 맞춰 자연스럽게 결정. **target 길이를 강제하지 않는다**: 단순 변경이면 짧고, 정리할 정보가 많은 단일 기능이면 길어진다. 다만 IDE 커밋 패널, `git log --oneline` 미리보기에서 자르지 않도록 다음 분량을 **hard cap**으로 둠.

### 정량 한도

| 항목 | 상한 |
|---|---|
| 전체 라인 수 (제목 + 빈줄 + 본문) | **23줄** |
| 본문 내용 줄 수 (빈줄 제외) | **17줄** |
| 본문 단락 수 | **5개** (배경 1 + 변경 4) |
| 단락당 줄 수 | **5줄** |
| 배경 단락 줄 너비 (bullet 은 접지 않음) | **약 50자** (영문은 72자) |
| 제목 (1행) | **60자** |

### 형식 reference

분량이 아니라 **형식**을 그대로 따른다: 제목 한 줄(`<type>(<scope>): <요약>`) → 빈줄 → 배경 단락(왜/무엇 해결) → 빈줄 → bullet(`- ` 시작, 명사형 종결).

**예시는 6) 모범 예시 한 곳에만 둔다.** 형태가 필요하면 그쪽을 보고 골격을 가져온다. 두 자리에 예시를 두면 톤이 갈려 어느 쪽을 따를지 흔들린다.

### 한도 초과 시 처리 우선순위

1. **변경을 둘로 쪼개 별도 commit**: 가장 우선. 한 commit에 두 가지 이상의 의도가 섞여 있으면 무조건 분리(상단 "한 commit에 한 기능만" 룰 참조).
2. **bullet을 명사형 한 줄씩으로 압축**: 보조 들여쓰기 항목 제거, 같은 정보 중복 bullet은 상위 하나로 통합.
3. **배경 단락 압축**: why 한 문장 + 트레이드오프 한 문장이면 충분. PR 설명/이슈로 옮길 맥락은 옮김.
4. **배경 단락만 줄바꿈**: 한국어 50자, 영문 72자에서 접음. bullet 은 접지 않고 문장을 줄임(6) 골격).

### Self-audit (commit 직전 필수)

작성한 메시지가 위 상한(23줄, 17줄 본문, 5개 단락, 배경 단락 50자 wrap, 60자 제목) 중 하나라도 넘으면:
- 자동 압축이 가능하면 직접 압축 후 진행.
- 압축이 어려우면 commit 분리 시도(한 commit에 두 의도가 섞였을 가능성).
- 분리/압축 모두 어려우면 사용자에게 한 줄 보고: "본문 N줄로 초안 작성: 줄여서 진행할지 그대로 둘지 선택?"

분량은 변경 내용에 맞춰 자연스럽게 결정. **짧은 게 미덕도, 긴 게 미덕도 아니다**: 형식과 한도만 지키면 OK.

## 3) type 선택 가이드

| type | 용도 |
|---|---|
| `feat` | 신규 기능. 새 라우터, CLI 명령, 모듈, UI 흐름. 동작 표면이 늘어남. |
| `fix` | 버그 수정. 사용자 영향 동작이 변경되어 회귀가 보호되는 경우 포함. |
| `docs` | 문서만 변경: README, docs/, 모듈 docstring, comments. |
| `refactor` | 동작 변경 0의 구조 개선. 모듈 분리, rename, 내부 헬퍼 이동. |
| `test` | 테스트만 추가/수정. 코드 변경이 동반되면 그쪽 type 사용. |
| `chore` | 빌드 메타, 로깅, 정리, .gitignore, 미세 cleanup. |
| `style` | 포매팅, 공백, import 순서만. |
| `build` | 의존성, 빌드 시스템, pyproject 변경. |
| `ci` | CI 워크플로우/hook 설정. |

추론 규칙:
- 변경 파일이 `*.md` 또는 `docs/*` 만 → `docs`
- 변경 파일이 `tests/*` 만 → `test`
- 새 함수, 라우터, CLI 명령, UI 요소가 추가 → `feat`
- 기존 함수/라우터의 동작이 바뀌어 회귀 보호가 필요 → `fix`
- 위 어느 것도 아니면 `chore` 또는 `refactor`로 결정

**`<scope>` 결정** (필수):
- 변경의 **중심 디렉토리, 모듈, 기능 영역**을 한 단어로. 예: `frontend/src/utils/*` → `utils`, 컴포넌트 뷰 → `ui`, 백엔드 라우터 → `api`, CSV 가져오기 → `import`.
- 여러 영역에 걸치면 변경량/의도의 **중심** 하나만. (여러 영역에 두루 걸치면 commit 분리 신호: 위 "한 commit에 한 기능만" 재검토.)
- 한 대상으로 도저히 못 좁히는 드문 경우만 scope 생략.

## 4) 동작 절차

1. **변경 진단** (병렬로):
   - `git status --short`: staged + unstaged + untracked 목록
   - `git diff --stat HEAD`: 파일별 변경 통계
   - `git diff HEAD` 또는 `git diff --cached` (큰 변경이면 요약만)
   - `git log --oneline -10`: 최근 커밋 톤 참고
   - `git log <base>..HEAD --oneline`: 이 브랜치 앞선 커밋(흡수 판단용)
2. **흡수 판단** (위 0) 섹션):
   - 이번 변경이 앞선 커밋의 후속 손질(같은 기능)이면 **흡수**(HEAD면 `--amend`, 더 앞이면 fixup+autosquash), 새 기능이면 **별도 commit**. 애매하면 한 줄 확인.
   - 흡수로 정했어도 아래 **3) 안전 가드/4) 경량 검증은 먼저 거친다**. 그 뒤 0) 흡수 절차로 커밋(별도 commit 의 메시지 작성 절차는 건너뜀).
3. **안전 가드**:
   - `.env` / `*.key` / `*credentials*` / `*secret*` 등 비밀 파일이 staged 또는 untracked로 보이면 즉시 중단/경고. 사용자 명시 승인 없이는 commit 진행 X.
   - `git add .` / `git add -A` 사용 금지: 변경 파일을 명시적으로 add.
4. **커밋 전 경량 검증** (위 0.5) 섹션):
   - 0.5) 의 생략 조건(docs/chore 전용, 실행 로직 무변경, `--no-verify-agents`)이 아니면 **리뷰 에이전트 1개(Claude Code 는 Explore, haiku, effort low)가 네 렌즈를 한 번에 리뷰** → 안전한 발견 직접 수정.
   - 수정으로 코드가 바뀌면 이후 stage/커밋(, 흡수)은 그 최종 상태 대상. 범위 벗어난 대규모 리팩터는 제안만.
5. **stage 결정**:
   - 사용자가 미리 stage 안 했고 untracked/modified 파일이 있으면 사용자에게 어떤 파일을 stage할지 확인. 명백한 경우는 의도 추정해 명시 add.
6. **type, scope, 요약 작성**:
   - 위 추론 규칙으로 type/scope 결정. scope는 주로 다룬 대상(필수).
   - 한 줄 요약은 변경의 핵심을 명사형 한 문장으로.
7. **본문 작성**:
   - 첫 단락: 변경 배경/맥락 1-3줄.
   - bullet list: 세부 변경 항목들. 같은 파일 안의 여러 변경은 한 bullet에 묶거나 들여쓰기 보조 항목으로.
   - **2) 분량 상한 표를 충족하는지 self-audit**: 본문 17줄 / 단락 5개 / 배경 단락 50자 wrap 등.
8. **commit 실행**:
   - heredoc으로 멀티라인 메시지 안전 전달:
     ```cmd
     git commit -m "$(cat <<'EOF'
     <type>(<scope>): <요약>

     <본문 단락>

     - <bullet 1>
     - <bullet 2>
     EOF
     )"
     ```
   - `--amend`, autosquash 는 **0) 흡수 경로에서만** 사용. 별도 commit 경로에서는 `--amend` 금지(사용자 명시 요청 없으면). pre-commit hook 실패 시 새 commit 만들지 말고 원인 fix 후 재시도.
   - `--no-verify` 사용 금지(사용자 명시 요청 없으면).
9. **결과 보고 + 커밋 단위 멘토 설명**:
   - `git status` 한 줄 + `git log --oneline -1`로 직전 commit 확인.
   - **이 커밋이 담은 작업을 멘토 방식으로 설명한다**: 글로벌 `~/.codex/AGENTS.md` 의 Mentor 섹션 기준: 구조, 로직, 데이터 흐름 + 근거, 트레이드오프, 사각지대(blind spot) + 업계 통례 대비 위치, 컴공 1학년 눈높이(용어는 풀어서).
   - 여러 커밋을 냈으면 **각 커밋별로 분리**해 설명(한 덩어리로 뭉치지 않음). 흡수(`--amend`/fixup)로 기존 커밋에 합친 손질도 그 작업을 설명.
   - **비례적으로**: 사소한 chore, 문서, 설정 커밋은 축약(핵심 한두 줄). 의미 있는 구현일수록 충실히.

## 5) 인자(`$ARGUMENTS`) 처리

- 사용자가 `/commit "lint 정리 + import 순서"` 같이 추가 메모를 주면 본문 첫 단락에 그 내용을 자연스럽게 녹임.
- 사용자가 `--type feat` 같은 명시적 옵션을 주면 그대로 따름.
- 인자 없으면 자체 추론.

## 6) 모범 예시

아래 세 건이 **목표 형태**다. 실제 커밋의 골격을 그대로 두고 도메인만 CSV 가져오기 서비스로 바꾼 예시이고, 사용자가 이 골격을 기준으로 삼는다. 앞 둘은 `fix`, 마지막은 `feat` 이며 골격은 type 과 무관하게 같다. 배경 단락의 **끝맺음**은 세 가지 꼴(명사형, 음슴체, `-던 문제였음`)을 보이도록 골랐다.

```
fix(import): 업로드 폴더 권한과 링크 정리 복구

읽기 권한이 없는 압축 해제본과 폴더 밖 심볼릭 링크 때문에
가져올 파일이 누락되고 업로드 정리까지 막힘.

- 디렉터리 탐색권과 파일 읽기 권한 보정(normalizeExtractedDir)
- 폴더 밖/끊어진 심볼릭 링크 제거 및 실패 시 처리 중단
- 삭제 재시도 전 디렉터리 권한 복구(restoreDirPermissions)
- 압축 해제와 정리 회귀 테스트 추가
```

```
fix(import): 실패 워커와 빈 결과 진단 정정

워커 종료 코드만으로 정상 처리를 단정하고 가져온 행 0건을
숨겨 운영 원인을 반대 방향으로 안내함.

- 종료 우선순위와 로그 토큰으로 워커 상태 판정(workerStates)
- 가져오기 준비 확인 결과에 행 수 포함(isImportReady)
- 빈 결과와 일부 성공 문구를 완료/실패 경로에 반영
- 워커 조합과 준비 상태 회귀 테스트 추가
```

```
feat(import): 가져오기 진단 저장과 불완전 결과 경고

워커가 죽어 가져온 행이 0건이어도 화면이 '완료' 로만 보여
가져오기가 성공한 것으로 오인되던 문제였음.

- 확정 시점 워커 상태/행 수를 진단으로 저장(lastImportDiag)
- 업로드 파일 검사 결과를 진단까지 전달(fileValidated)
- 재업로드 시 직전 진단 클리어(CLEARED_IMPORT_DIAG)
- 불완전 판정과 빈 결과 문구를 상세 화면 경고로 분기(isImportDegraded)
```

### 이 세 예시에서 읽어야 할 골격

| 자리 | 규칙 |
|:---|:---|
| 제목 | `<type>(<scope>): <명사구>`. 20자 안팎으로 짧게. 무엇을 어떻게 했는지만 |
| 배경 | **2줄**. 원인과 증상을 한 문장에 담고 50자에서 접음. 끝맺음 꼴은 문장에 맞게 고름 |
| bullet | **한 항목당 한 줄**. wrap 하지 않음. 넘치면 문장을 줄이지 접지 않음 |
| 식별자 | 항목 **끝 괄호**에 몰아 적음. `보정(normalizeExtractedDir)`. 문장 중간에 흩지 않고, 이 괄호 안에서는 백틱을 생략 |
| 전체 | 9줄. 제목 1 + 빈줄 + 배경 2 + 빈줄 + bullet 4 |

배경 단락이 **원인과 증상을 한 문장에 담는다**는 점이 핵심이다. 무엇 때문에(원인) 무엇이 어떻게 됐는지(증상)를 한 덩어리로 쓰고, 원인 분석이나 해결 방법은 배경에 넣지 않는다. 그건 bullet 이 맡는다.

**끝맺음에 정해진 꼴은 없다.** 완결형 종결(`-했다`, `-된다`, `-있었다`)만 피하고 개조식으로 깔끔하게 닫으면 된다. 위 세 예시가 각각 `막힘.`(명사형), `안내함.`(음슴체), `-던 문제였음.` 으로 끝나는 것이 그 뜻이다. 이 레포 커밋에는 `죽음.`, `분리함.`, `띄움.`, `상태.`, `퍼짐.` 도 쓰인다.

**문장이 먼저이고 어미가 나중이다.** 어미 하나를 정해 두고 문장을 거기에 맞추면 말이 뒤틀린다. 쓰고 나서 소리 내 읽었을 때 걸리지 않는 쪽을 고른다.

세 예시 모두 **마지막 bullet에서 끝남**. 이 형식을 그대로 따른다.

## 7) 어투 규칙 (모든 commit 메시지에 공통 적용)

- **개조식 한국어: 명사형 + 음슴체를 내용에 맞게 섞는다.** 금지되는 것은 완결형 서술 종결("-했다/-였다/-한다/-된다/-있었다") 하나뿐. 제목은 명사형 고정, 배경 단락과 bullet 은 아래 기준으로 고른다.
    - **짧은 항목/나열은 명사형**: `가릴 필드에 최종 수정자 추가(updatedBy(Name))`, `회귀 테스트 4건`
    - **인과/경위를 풀어야 하는 문장은 음슴체**(-음/-함/-됨/-임/-았음/-었음). 서술 구조는 그대로 두고 종결만 바꾼다: `작성자 필드를 지워도 같은 사람이 수정자 필드로 노출됐음`
    - **판단 기준**: 명사형으로 끊었을 때 어색하거나 명사가 3개 이상 연달아 쌓이면 그 자리가 음슴체 자리. 억지로 명사를 쌓으면 개조식이 아니라 그냥 읽기 어려운 글이 됨
    - 나쁜 예: `필드를 지워 전송. 그런데 이름이 그대로 잔존` → 좋은 예: `필드를 지워 보냄. 그런데 이름이 그대로 남아 있었음`
- **간결**: 한 항목 한 줄. 길어지면 문장을 줄임.
- **why를 본문 단락에**, **what을 bullet에**. 변경 자체보다 왜 바꿨는지를 본문이 설명.
- **부정확한 형용사/감탄 회피**: "완벽히", "엄청나게", "획기적" 같은 표현 금지. 사실 진술.
- **식별자는 보조로 반드시 넣는다**: 기능적 서술이 주이고, 바뀐 필드, 함수, 파라미터, 상수 이름을
  그 서술에 앵커로 붙인다. 둘 중 하나만 있으면 실패다.
    - 이유: 기능만 있으면 나중에 `git log -S<식별자>`, `git log --grep` 으로 못 찾고,
      리뷰어가 diff 어느 줄 이야기인지 눈으로 맞춰야 함. 식별자만 있으면 무엇이
      달라졌는지가 안 읽힘
    - 나쁜 예(기능만): `가릴 필드에 최종 수정자(사번/이름)와 원본 파일명 추가`
    - 나쁜 예(식별자만): `HIDDEN_FIELDS 에 updatedBy, updatedByName, sourceFileName 추가`
    - 좋은 예: 가릴 필드에 최종 수정자/원본 파일명 추가(updatedBy(Name), sourceFileName)
    - 앵커를 붙이는 곳: 바뀐 필드, 상수, 함수명, 새 파라미터와 기본값, 상태값/enum,
      설정 키, 공개 API 경로. 이름이 없으면 리뷰어가 그것을 특정할 수 없는 자리다
    - 앵커를 빼는 곳: 배경 단락(why 는 기능적 서술로만), 변경 없이 스쳐 지나간 파일명,
      테스트 파일명(건수로 적는다), 같은 이름을 bullet 마다 되풀이하는 것
- **고유 명사/코드 식별자는 원문 그대로**: `ImportJobPayload`, `SKIP fast-path` 등. 번역하지 않는다.

## 8) 종료

commit 성공 시 짧게 한 줄 보고 (예: `[main abc1234] <type>(<scope>): <요약>`). 실패면 원인 + 다음 단계 안내.
