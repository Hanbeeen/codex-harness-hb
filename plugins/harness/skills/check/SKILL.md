# /check: code-review + security-review + simplify + qa 통합 점검

현재 변경분을 네 패스로 점검한다: **정확성 버그 → 보안 취약점 → 품질 정리 → 런타임 동작 검증.**
인자(Claude Code 는 `$ARGUMENTS`)가 PR 번호, 브랜치, 파일 경로면 그 대상을, 강조점 메모면 각 패스에 전달한다.

1-3 패스는 Claude Code 에 내장된 스킬(`code-review`, `security-review`, `simplify`)이 있으면 그 스킬을 호출하고, 없는 환경(Codex)이면 각 패스에 적은 렌즈로 메인이 변경분을 직접 읽어 점검, 수정한다.

## 실행 순서: 버그 → 보안 → 정리 → 동작 검증

버그, 취약점 있는 코드를 정리, 검증하면 헛수고이고, 검증은 다 고친 최종 코드에 해야 의미가 있으므로 **이 순서를 지킨다.**

### 1) code-review: 정확성 버그
- `code-review --fix` 로 스킬 호출(인자 있으면 함께 전달). 정확성 버그 점검 + **수정**. `--fix` 가 없으면 보고만 하고 수정을 적용하지 않는다.
- 직접 점검할 때의 렌즈: 로직 오류, 경계값, 널/예외 처리, 상태 불일치, 동시성, 호출자 계약 위반.
- 이 패스가 끝까지 완료(수정 적용 포함)된 뒤에만 2)로.

### 2) security-review: 보안 취약점 (조건부 발동 + 자동 수정)
- **먼저 이번 변경분이 보안 점검 가치가 있는지 판단한다.** 아래 "보안 검사 발동 조건" 중 하나라도 해당하면 실행, 아니면 **건너뛰고 그 사실(사유)을 알린다**.
- 실행 시 `security-review` 스킬(= 내장 `/security-review`)을 호출하거나, 없으면 직접: 현재 브랜치의 pending 변경분을 대상으로 취약점을 점검한다. 인젝션(SQL/NoSQL/command), 경로 탐색, 인증/인가 결함(권한 누락, IDOR, 토큰 검증), 민감정보/시크릿 노출, SSRF/XSS/CSRF, 안전하지 않은 역직렬화, 리다이렉트, 암호화 사용 등. 강조점 인자가 있으면 함께 전달.
- security-review 는 기본이 **보고 중심(자동 수정 안 함)**이므로, 보고된 발견을 받아 **이 패스에서 직접 수정한다(자동 수정).** 적용 기준:
  - **High/Critical + 발견이 확실(confirmed)** → 변경 범위 안에서 직접 수정.
  - 수정이 **설계 판단, 동작 변경, 범위 확장**을 요하거나 발견이 **불확실, 저신뢰** → 자동 수정하지 말고 **제안으로만 보고 + 사용자 확인**.
  - **비가역/광범위 영향**(인증 흐름 전면 변경, 스키마/마이그레이션, 외부 계약 변경 등)은 착수 전에 **먼저 알리고 확인을 구한다**.
- 자동 수정 후 **재점검 루프는 돌지 않는다**: 한 번 수정 + 보고가 범위. 추가 검증이 필요하면 사용자 판단으로 다시 호출한다.
- 이 패스가 끝까지 완료된 뒤에만 3)으로.

**보안 검사 발동 조건** (하나라도 해당하면 실행):
- 새로/변경된 **API 라우트, 엔드포인트**, 요청 파라미터, 바디, 헤더 처리
- **인증/인가, 권한 체크**(권한 게이트, 토큰/세션/JWT, 역할 평가) 변경
- **사용자 입력**이 DB 쿼리, 파일 경로, 셸 명령, 외부 HTTP 요청에 닿는 경로 (injection, path traversal, SSRF)
- 사용자 제공 콘텐츠의 **렌더링/저장**(XSS: 예: 리치 텍스트/HTML 본문, 템플릿 주입)
- **파일 업로드/다운로드**, 파일시스템 접근, 압축 해제
- **시크릿, 토큰, 자격증명** 취급, 로깅, 외부로 흘러가는 경로(응답, 로그, 서드파티)
- 암호화, 해시, 난수, 직렬화/역직렬화, 리다이렉트, CORS, 쿠키, CSP 설정, 의존성 추가

**건너뛰는 경우**: 변경이 순수 UI 스타일/레이아웃, 카피 텍스트, 문서, 설정/로깅, 위 표면을 건드리지 않는 리팩터 등 **보안 표면이 없을 때**. (인자에 `--no-sec` 면 판단과 무관하게 건너뜀.)

### 3) simplify: 품질 정리
- 1, 2)로 수정된 최신 상태 기준, `simplify` 스킬 호출(없으면 직접). 재사용, 단순화, 효율, 추상화 정리 + **수정**.
- 정확성 버그/보안 취약점은 다시 찾지 않음(1, 2)가 담당). ⚠️ 정리하다 1, 2)의 수정(버그 fix/보안 패치)을 되돌리지 않도록 주의.

### 4) qa 검증: 런타임 동작 (읽기 전용)
- 1, 2, 3)으로 고쳐진 **최종 코드가 실제로 동작하는지** `/qa` 커맨드로 검증한다(인자 있으면 전달).
- 앱을 구동해 런타임 표면(HTTP, UI, CLI)까지 몰아 관찰하고, **명세 위반, 회귀, 엣지케이스 버그를 적대적으로** 찾아 보고. 발견은 **재현 입력/상태 + 관찰된 잘못된 출력**으로 입증.
- ⚠️ `/qa` 는 **코드를 수정하지 않는다**. 발견은 보고만. 단 QA 프로필이 없는 레포에서는 첫 실행에 프로필 파일을 만들므로, 커밋할 때 그 파일을 섞지 않는다.
- qa 가 런타임 버그를 찾으면 보고하고: **사용자 판단에 따라** 다시 1)로 돌려 고친다. **자동 무한 루프는 돌지 않는다.**
- 앱을 구동할 수 없어 런타임 확인을 못 하면 그 범위를 건너뛴 사실을 함께 보고한다.
- qa 스킬이 없는 환경(Codex 에서 node 가 없어 설치되지 않은 경우)이면 이 패스를 건너뛰고 그 사실을 보고한다.

## 통합 보고

네 패스가 끝나면 합쳐서 보고:

- **버그(code-review)**: 무엇을 고쳤는지 / 건너뛴 것
- **보안(security-review)**: 발동 여부(+사유) / 자동 수정한 것 / 제안만 한 것(확인 필요) / 깨끗 / 건너뜀
- **정리(simplify)**: 무엇을 고쳤는지 / 건너뛴 것
- **동작(qa)**: 발견(재현/관찰 포함) / 깨끗 / 건너뜀(사유)
- 모든 패스가 깨끗하면 그렇게 명시.

## 생략 조건

- 인자에 `--no-qa` 면 4) qa 패스를 건너뛰고 정적 점검(1, 2, 3)만.
- 인자에 `--no-sec` 면 2) security-review 패스를 건너뛴다(발동 조건 판단도 생략).
- 변경이 `*.md`, `docs/*` 만이거나 순수 `chore`(설정, 로깅, .gitignore)면 점검 가치가 낮아 생략 가능. 코드 변경이 섞였으면 생략하지 않음.

## 주의

- **커밋/push 하지 않는다.** 점검 + (수정 패스들의) 수정까지가 범위. 커밋 정돈은 `/recommit`, 커밋은 `/commit`, PR 텍스트는 `/pr-draft`.
- ⚠️ **범위 보존**: 점검이 원래 요구사항 범위를 벗어난 대규모 리팩터를 제안하면 적용하지 말고 제안만 보고한다. 보안 자동 수정도 동일: 변경분의 취약점을 닫는 데 그치고, 무관한 코드까지 손대지 않는다.
- 내장 스킬이 있으면 code-review, simplify, security-review 의 세부 정책은 각 스킬이, qa 는 `/qa` 커맨드가 단일 소스: `/check` 는 순서만 엮는다. 내장 스킬이 없으면 이 문서의 렌즈가 기준이다.
