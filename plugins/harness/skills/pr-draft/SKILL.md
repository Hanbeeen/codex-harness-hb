# /pr-draft: 사람이 직접 올리는 PR 제목/본문 작성

현재 브랜치와 base 브랜치(기본 `main`)의 차이를 진단해 **PR 제목과 본문만** 작성한다.
사용자가 Bitbucket/GitHub 등에 직접 복사, 붙여넣기로 올린다. 이 skill 은 텍스트를 만들 뿐이다.
PR 텍스트 작성 **전에 브랜치명이 커밋들의 공통 토픽과 맞는지 한 번 점검**한다(아래 "작성 절차" 1).

## ⚠️ 절대 금지

- **PR 을 직접 보내지 말 것.** `gh pr create`, Bitbucket API, 그 외 어떤 방식으로도 PR/MR 을
  직접 생성/제출하지 않는다. 사용자가 직접 업로드한다.
- **`git push` 도 실행하지 말 것.** push 는 사용자 몫. 이 skill 의 범위는 PR 텍스트 작성(+ 로컬 브랜치 rename)까지.
- **브랜치 rename 은 로컬만** (`git branch -m`). **원격 브랜치 push, 삭제, 이름변경 금지.** 이미 push 된
  브랜치면 rename 하지 말고 새 이름을 **제안만** 한다(원격 정리는 사용자 몫).
- **PR 내용 외 텍스트 금지.** "여기 PR 초안입니다" 같은 안내, 머리말, 꼬리말 전부 금지. 답변은
  **`제목`, `본문` 라벨 + 두 코드블록뿐**. **유일한 예외**: 브랜치 rename(또는 제안)을 했을 때
  **그 한 줄만** PR 블록 위에 둘 수 있다(예: `브랜치명 변경: feature/a → feature/b`).
- **AI 가 쓴 티가 나는 요소 일절 금지** (아래 "자연스러움 규칙" 참조).

## 출력 형식

제목과 본문을 **각각 별도 코드블록**으로 출력한다. 블록마다 복사 버튼이 따로 생기도록.
각 코드블록 바로 위에 `제목` / `본문` 라벨 한 줄만 둔다. 그 외 안내 텍스트는 넣지 않는다(브랜치
rename 한 줄은 위 예외대로 허용).

제목
````
```
<제목: 한 줄, 변경의 핵심>
```
````

본문
````
```
## 배경
<왜 이 변경이 필요한지: 문제/맥락. 짧은 단락 또는 bullet>

## 변경
<무엇을 바꿨는지. 갈래가 여럿이면 갈래별 #### 소제목 + 평 bullet, 단순하면 평 bullet>

## 검증
<테스트, 타입체크, lint 결과, 또는 영향 범위>
```
````

- **제목**: 변경의 핵심을 한 줄로. `<영역>: <요약>` 형태(예: `운영 위험 툴팁: …`). 복수 변경은
  `+`로 묶음(예: `… 1-hop 단축 + None 툴팁 정리`). 마침표 없음. 개조식 명사형.
- **섹션 구성**: 기본 3섹션: `## 배경`(왜) → `## 변경`(무엇) → `## 검증`(결과/영향).
  - 헤더 명칭은 내용에 맞게 자연스럽게: `## 배경`↔`## 개요`, `## 변경`↔`## 변경 사항`,
    `## 검증`↔`## 영향 범위`.
  - **변경이 사소하면 섹션을 줄인다**: 예: `## 개요` + `## 변경 사항`만, 또는 `## 변경` 하나만.
    규모에 맞춰 가감. 작은 변경에 3섹션을 억지로 채우지 않는다.
- **`## 변경` 안 구성**: 변경이 두세 갈래로 나뉘면 **갈래별 `####` 소제목**(`#### 1. 제목`)으로 갈래를
  세우고, 소제목 **바로 다음 줄**에 핵심을 **최상위 평 bullet**(`-`)로 둔다. 소제목과 bullet 사이,
  그리고 bullet 끼리도 빈 줄을 넣지 않고 촘촘히 붙인다(빈 줄은 갈래와 갈래 사이에만 하나).
- **소제목 vs bullet 역할(2계층)**: `#### 번호. 제목` 소제목은 **무엇이 바뀌었나**(기능/동작 단위, 도메인
  관점), 그 아래 bullet 은 **어떻게/왜**(구현, 메커니즘, 근거, 서비스 관점). 이 2계층은 **세부 bullet 이
  갈래당 하나뿐이어도 유지**한다(소제목을 생략해 한 줄로 접지 않는다). 변경이 **정말 단일 갈래**일 때만
  소제목 없이 평 bullet 로 둔다.
- **⚠️ 중첩 리스트 금지**: 번호/불릿 아래에 들여쓴 하위 bullet(중첩)은 쓰지 않는다. Bitbucket 등
  다수 렌더러가 번호 리스트 아래 들여쓴 하위 bullet 을 중첩으로 인식하지 못해, 하위 항목이 부모에
  이어지는 한 줄로 뭉치고 `-`/`*` 마커가 리터럴로 노출된다. 갈래는 반드시 위처럼 `####` 소제목 +
  바로 이어지는 최상위 평 bullet 로 표현한다(들여쓰기로 계층을 만들지 않는다).
- 언어는 저장소 commit/문서 언어를 따른다(이 저장소는 한국어). 어투는 개조식.

## 무엇을 담는가: 심볼 범벅도, 장황한 풀이도 아닌 압축

PR 본문은 **구현한 기능이 무엇을 하는지/왜 중요한지**를 설명한다. 리뷰어가 알고 싶은 건 "코드에
무엇을 추가했나"가 아니라 "이 변경으로 무엇이 어떻게 동작하게 됐나"다.

**양쪽 다 실패다.** 한쪽만 피하려다 반대쪽으로 넘어가는 일이 잦으니 두 실패 모드를 같이 본다.

- **실패 A: 심볼 범벅**: 파일명, 함수명, 변수명을 줄줄이 나열한 변경 목록.
    - 나쁜 예: "`getDeclarations()` 추가, `extractPaths()` 분리, `Foo.vue` 수정"
- **실패 B: 장황한 풀이**: "쉽게 설명한답시고" 직관적이지도 않은 한국어로 길게 늘여 쓴 것.
  용어를 억지 번역해 오히려 무엇을 가리키는지 모호해지고, 한 줄이면 될 것이 세 줄이 된다.
    - 나쁜 예: "파일 요약값이 없어 같은 기준으로 비교할 수 없는 경우에는 값을 만들지 않도록 하여
      화면에 잘못된 정보가 표시되지 않게 함" (checksum 을 "파일 요약값"으로 번역해 지시 대상이 흐려짐)
    - 좋은 예: "checksum 이 없으면 비교하지 않고 '확인 불가' 표기. 없음으로 적으면 저장소에 같은
      파일이 있을 때 오표기"

### 압축 기준

- **핵심만 남긴다.** 의미가 변하거나 못 알아먹지 않는 선에서 최대한 짧게. 한 bullet 은 한 줄,
  길어도 두 줄. 같은 말을 다르게 반복하지 않는다.
- **⚠ 분량 상한(hard cap).** 리뷰어는 PR 본문을 읽으러 온 것이 아니라 diff 를 보러 온다.
  본문이 화면을 넘기면 안 읽고 코드로 내려간다. 아래를 넘으면 압축하거나 PR 을 쪼갠다.
    - 본문 전체 30줄(빈 줄 제외), `## 배경` 4줄, 갈래(`####`) 4개, 갈래당 bullet 3개, `## 검증` 3줄
    - bullet 은 한 줄이 기본. 두 줄을 넘기면 그 bullet 은 두 가지를 말하고 있다
    - 넘겼을 때 순서: 갈래 통합 → bullet 통합 → 배경 압축 → PR 분할. **문장 다듬기로
      줄이려 하지 않는다.** 길이는 문장이 아니라 항목 수에서 나온다
    - 뺄 것을 고르는 기준: 리뷰어가 diff 를 보면 아는 것(구현 방식/자료구조), 안 바꾼 것을
      굳이 밝히는 줄, 같은 결정을 두 갈래에서 되풀이하는 줄. 남길 것은 이 변경으로 달라진
      결과와, 그렇게 한 이유 중 리뷰어가 판단하는 데 필요한 것. "이걸 빼면 이렇게 깨진다" 같은
      가정 경고는 코드 주석에 둘 내용이라 PR 에 쓰지 않는다
    - 작성 후 줄 수를 세어 확인한다. 눈대중은 매번 늘어난다
- **⚠ 우선순위: 기술적 정확성 > 기능적 표현 > 심볼 나열 절제.** 아래 항목들은 이 순서 안에서만
  적용한다. 쉽게 쓰려다 원래 동작보다 넓거나 좁은 말이 되면 그건 압축이 아니라 오기이고, 그럴
  바에는 심볼/기술용어를 그대로 쓰는 편이 낫다. 특히 범위(전사, 프로젝트, 버전), 조건(언제 걸리나), 
  저장 단위/실패 방향은 풀어 써도 정확히 같은 것을 가리켜야 한다.
    - 나쁜 예: "되돌림 검증을 더 꼼꼼하게" (무엇이 어떻게 달라졌는지 사라짐)
    - 나쁜 예: "시트별로 매핑을 관리하도록 변경" (저장소의 저장 단위 이야기인데 주체가 매핑으로 바뀜)
    - 좋은 예: "열 매핑 검증이 파일당 한 번만 확인하던 것을 시트마다 확인"
- **서술이 주, 식별자는 앵커.** 무엇이 어떻게 달라졌는지를 동작으로 적고, 그 서술이 가리키는
  대상의 이름을 괄호에 붙인다. 막으려는 것은 "이름을 쓰는 것"이 아니라 "이름만 줄줄이
  나열하는 것"이다. 이름이 앞에 깔려 주어 자리를 차지하면 정작 무엇이 달라졌는지가 안 읽히고,
  이름이 아예 없으면 리뷰어가 diff 어느 줄 이야기인지 눈으로 맞춰야 한다.
    - 나쁜 예(이름이 주어): "`maskForeignOwner` 가 응답 배열을 지나며 개인정보 12개 필드 삭제"
    - 나쁜 예(이름이 통째로 없음): "응답을 내보내기 직전 접근권한을 확인하고, 없으면 개인정보를 지움"
    - 좋은 예: "응답을 내보내기 직전 원본 워크스페이스별로 접근권한을 확인하고, 없으면 개인정보를
      지움(`maskForeignOwner`)"
    - 나쁜 예: "`resolveWorkspaceScope` 가 종류별 허용집합을 인자로 받도록 변경"
    - 좋은 예: "종류별 허용 범위를 상수 한 곳에서만 정하도록 정리(`resolveWorkspaceScope` 가
      허용집합을 인자로 받음)"
- **앵커를 붙이는 곳과 빼는 곳.** 아무 데나 붙이면 심볼 범벅으로 되돌아간다.
    - 붙이는 곳: 이번에 바뀐 필드, 상수, 함수명, 새 파라미터와 기본값, 상태값/enum, 설정 키,
      공개 API 경로, 마이그레이션 대상 컬럼. 리뷰어가 diff 에서 찾아가야 할 자리다
    - `## 배경`에도 붙인다. 단 문제를 특정하는 데 필요한 것만(어느 필드가 새고 있었나,
      어느 값이 어긋났나). 배경은 왜 인지를 말하는 자리라 밀도는 `## 변경`보다 낮게
    - 빼는 곳: 변경 없이 스쳐 지나간 파일명, 이미 앞 bullet 에 나온 같은 이름,
      명령어/도구 이름(`npx vue-tsc --noEmit` 대신 "타입체크 통과"), 개별 테스트
      파일명(건수 또는 "Windows 에서만 나던 기존 실패" 처럼 성격으로)
- **정확히 못 쓰겠으면 심볼, 기술용어를 그대로 쓴다.** 이름, 경로, 필드, 용어를 빼고는 무엇을 가리키는지
  특정할 수 없거나 뜻이 흐려지는 자리라면 원문 그대로 쓴다(설정 키, 공개 API 경로, 마이그레이션
  대상 컬럼, 상태값, 프로토콜/표준 용어 등). 쓰기로 했으면 얼버무리지 말고 정확히 쓰되, 같은
  이름을 문단마다 반복하지는 않는다.
- **도메인 용어는 번역하지 않는다.** 그 제품/팀이 대화에서 실제로 쓰는 말(checksum, upsert,
  dedupe, 시트, 원본 행, 상시 규칙 등)은 원문 그대로. 이건 구현 심볼이 아니라 업무 언어다. 번역하면
  지시 대상이 모호해져 "쉬워지는" 게 아니라 안 읽힌다.
- **개념은 쉽게, 분량은 짧게.** 왜 그렇게 했는지(근거/트레이드오프)는 평이한 말로 쓰되 한 문장.
  배경 지식이 없어도 읽히게 하되, 교과서 설명을 옮겨오지 않는다.
- **자기만족 서술 금지.** "조건문이 아니라 코드를 삭제해서 되살리기 어렵게 함" 같은 구현 자랑은
  리뷰어가 diff 로 아는 내용이다. 동작이 달라지지 않는 서술은 뺀다.
- **한 갈래 = 한 의미 단위**: `## 변경`의 각 갈래(`####` 소제목)는 "구현 조각"이 아니라 "동작/사용자
  관점에서 의미 있는 변화" 단위로 묶음. 그 아래 평 bullet 은 무엇이 달라졌나와 왜를 동작으로
  보강하고 해당 식별자를 앵커로 붙임(심볼 나열이 아니라).
- **"그래서 뭐가 좋아지나"가 읽히게**: 각 변경이 해결한 문제/바뀐 결과가 문장에서 드러나도록.

### 직관적으로 쓰기: 한 번 읽고 알아듣게

기준은 동료에게 말로 설명하는 것이다. 소리 내어 읽었을 때 듣는 사람이 "그게 뭔 소리야" 또는
"그래서 그게 뭐?" 라고 되물을 bullet 이면 실패다. 되물을 말이 남으면 고쳐 쓰거나 뺀다.
위 압축 기준보다 이 절이 먼저다. 짧아도 못 알아들으면 소용없다.

- **결과부터 쓴다.** 첫머리는 무엇이 어떻게 달라졌나(화면, 파일, API 응답에서 보이는 것).
  그 결과를 내려고 거친 구현 경로(조회 필드 추가, 응답에 값 실음, 타입 확장)는 따로 bullet 로
  세우지 않는다. diff 에 다 보인다.
- **가정 경고를 쓰지 않는다.** "X 가 빠지면 Y 가 됨", "지우면 Z 로 퍼짐" 처럼 지금 일어나지 않는
  일은 적지 않는다. 리뷰어는 지금 바뀐 것을 보러 왔다. 그런 경고는 코드 주석에 둔다.
- **확인 안 한 이유를 옮겨 적지 않는다.** 코드 주석/커밋 메시지에 적힌 "왜"를 그대로 가져오지
  말고 사실인지 먼저 본다. 확인 못 하면 이유를 빼고 결과만 쓴다. 틀린 이유 한 줄이 본문 전체를
  못 믿게 만든다.
- **실제로 안 걸리는 분기는 쓰지 않는다.** 값이 없을 때의 폴백 같은 방어 코드는 실제 데이터에서
  걸리는 경우가 있을 때만 적는다.
- **bullet 하나에 말 하나.** 본론에 괄호 보충, '단,' 조건, 이유가 겹쳐 붙으면 무엇이 본론인지 안
  보인다. 본론만 남기고 나머지는 꼭 필요할 때만 다음 bullet 로 뺀다.
- 실제로 지적받은 예(2026-10-15):
    - 나쁜 예: "필드 없는 옛 문서는 '-'(담당자/생성 날짜와 같은 표기). 빈 칸이면 엑셀 필터/피벗이
      그 행을 빼서 미설정 워크스페이스가 목록에서 사라짐" (실제로 안 걸리는 분기 + 확인 안 한 이유 +
      괄호 보충이 한 줄에 겹침. 엑셀은 빈 칸 행을 빼지 않는다)
    - 나쁜 예: "전사 대상 조회 projection 과 행 응답에 `retentionScope` 추가. projection 에서
      빠지면 에러 없이 전 행이 빈 칸으로 나감" (구현 경로 + 가정 경고. 읽고 나면 "그래서 뭐?")
    - 좋은 예: "전사 가져오기 이력 CSV 의 파일명 뒤에 보관범위 열 추가. 워크스페이스 현황 CSV 와
      같은 이름/표기라 두 파일을 그대로 맞대 볼 수 있음"

## 자연스러움 규칙: 사람이 쓴 것처럼

- **이모지/장식 기호 금지**: 🚀 ✨ 📝, 화려한 구분선(`━━━`) 등.
- **표(table) 금지**: 사람이 PR 본문에 마크다운 표를 그리는 일은 드물다. bullet 으로 푼다.
- **불릿 마커는 `-` 로 통일**: unordered list 는 `-` 사용 (`*`, `+` 미사용). 하위 bullet 도 `-`.
- **섹션 헤더는 한국어로**: `## 배경` `## 변경` `## 검증` `## 개요` `## 변경 사항` `## 영향 범위`.
  영어 정형 헤더(`## Summary` `## Changes` `## Testing`)는 쓰지 않는다.
- **AI 상투어 금지**: "이 PR 은 X 를 도입합니다", "Additionally,", "Furthermore,", "전반적으로",
  "원활하게", "손쉽게", "강력한", "획기적" 같은 표현. 사실만 담백하게.
- **과한 bold/전수 나열 금지**: 변경 파일 전부 나열, 당연한 항목까지 bullet 로 부풀리지 않는다.
  단어마다 `**굵게**` 강조하지 않는다. 갈래 구분은 bold 가 아니라 `####` 소제목으로 한다.
- **개조식으로 작성**: 명사형과 음슴체(-음/-함/-됨/-임)를 내용에 맞게 섞는다. 금지되는 것은
  완결형 서술 종결("-했다/-한다/-된다/-합니다") 하나뿐. 짧은 항목/나열은 명사형, 인과/경위를
  풀어야 하는 문장은 음슴체. 명사가 3개 이상 연달아 쌓이면 그 자리가 음슴체 자리다.
  동료에게 변경을 설명하듯 짧고 담담하게.
- **의인화/비유 금지**: 코드/데이터를 사람처럼 쓰지 않는다. 무슨 일이 일어나는지 그대로 적는다.
  비유는 짧아 보이지만 실제 동작을 덮는다.
    - 나쁜 예: "행 하나를 작업 둘이 나눠 쥠" / "매핑이 서로 다툼"
    - 좋은 예: "저장소 쪽 기록은 하나인데 우리 쪽 가져오기 작업이 둘"
- **이 말들은 쓰지 않는다**: `고착`, `관측`. 개발 문서에서 잘 쓰지 않는데 유독 자주 튀어나오는
  말이라 그 자체로 티가 난다. (`차단`, `종결`, `무효화`, `정합성` 처럼 현업에서 실제로 쓰는 말은
  괜찮다. 횟수를 세지 않는다.)
    - `partial 에 고착` → "계속 실패로 남아 끝나지 않음"
    - `관측 불가` → "확인할 방법이 없음"

## 작성 절차

1. **base 브랜치 결정**: 인자로 받았으면 그걸, 없으면 `main`. (현재 브랜치가 `main` 이면 사용자에게
   어떤 브랜치/범위를 PR 로 볼지 한 줄로 확인.)
2. **변경 진단** (병렬로):
   - `git log <base>..HEAD --oneline`: 이 브랜치에 쌓인 commit 들 (PR 의 의도 파악 핵심)
   - `git diff <base>...HEAD --stat`: 파일별 변경 규모
   - 필요하면 `git diff <base>...HEAD` 로 핵심 변경 내용 확인 (큰 변경이면 요약만)
   - 테스트, 타입체크, lint 결과가 commit/diff 에 드러나면 `## 검증`에 반영. 모르면 추측해 지어내지
     않고 검증 섹션을 생략하거나 영향 범위로 대체.
3. **브랜치명 점검** (PR 작성 전 한 번):
   - 2)의 커밋들을 쭉 보고 **공통 토픽**을 잡는다. 현재 브랜치명(`git branch --show-current`)이
     그 토픽과 맞는지 판단.
   - **맞으면** 그대로 둔다(아무 것도 출력 안 함).
   - **엇나갔으면**(작업하다 주제가 옮겨가 원래 이름과 어긋남) 커밋들을 종합해 새 이름을 짓는다.
     네이밍은 글로벌 룰대로 **`feature/<토픽>`** (기존 브랜치 톤 따라 kebab-case).
     - 현재 브랜치에 **upstream 이 없으면**(미push) `git branch -m <새이름>` 으로 **로컬 rename** 실행.
     - **이미 push 됐으면**(`@{upstream}` 존재) rename 하지 말고 **새 이름 제안만** 한다(원격 정리는 사용자 몫).
   - rename/제안 했을 때만 PR 블록 위에 **한 줄** 표기: `브랜치명 변경: <옛> → <새>` 또는
     `브랜치명 제안(이미 push됨): <옛> → <새>`. 그 외 설명 없음.
4. **핵심 추출**: "이 PR 이 해결하는 것"을 잡아 `## 배경`에. 변경 갈래를 `## 변경`에 정리하되, 각
   갈래는 구현 조각이 아니라 **동작/의미 단위**로 묶고, 함수/파일명은 꼭 필요한 것만 최소한으로
   (위 "무엇을 담는가" 참조).
5. **제목/본문 작성**: 위 출력 형식 + 자연스러움 규칙대로.
6. **출력**: (브랜치 rename 한 줄 했으면 그 한 줄 →) `제목` 라벨 + 제목 코드블록, `본문` 라벨 +
   본문 코드블록. 그 외 텍스트 없음.

## 인자(`$ARGUMENTS`) 처리

- base 브랜치명(`develop`, `release/x` 등)을 주면 그 브랜치 기준으로 diff.
- "성능 위주로", "리뷰어가 마이그레이션 주의하게" 같은 메모를 주면 강조점에 반영.
- 인자 없으면 `main` 기준 + 자체 판단.

앵커 밀도도 두 예시가 대비를 이룬다. 첫 예시는 리뷰어가 diff 에서 찾아가야 할 필드/함수가

곧 앵커다. 붙일 것이 없으면 억지로 만들지 않는다.

첫 예시에서 특히 볼 것은 **앵커가 분량을 늘리지 않고 줄인다**는 점이다. 배경 첫 줄이 새던
필드 셋을 이름으로 지목하니, 종전에 그 셋을 말로 풀던 배경 두 줄이 통째로 필요 없어졌다.
이름 하나가 설명 두 줄을 대체한다.

그리고 이 예시는 **빼서** 29줄이 된 것이지 다듬어서가 아니다. 실제로 뺀 것은 세 종류다.
안 바꾼 것을 밝히는 줄(유지한 필드의 유지 이유), 앞뒤 섹션에서 같은 말을 되풀이하는 줄,
diff 를 열면 보이는 구현 방식(어느 값을 먼저 보고 없으면 무엇으로 폴백하는지). 길이를 줄일
때는 문장이 아니라 이 세 종류를 먼저 찾는다.
